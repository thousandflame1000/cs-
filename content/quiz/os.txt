@q os-11 | os-sync | 3
用號誌寫出 readers–writers 問題的一個解，使得「一旦有寫者在等待，新來的讀者就不能進入」（寫者優先），並說明在你的解中讀者是否可能飢餓。
---
號誌：`rw=1`（資源）、`rmutex=1`、`wmutex=1`（保護計數）、`readTry=1`（寫者等待時擋住新讀者），計數 `rc=0, wc=0`。
```c
writer:
  wait(wmutex); wc++; if (wc == 1) wait(readTry); signal(wmutex);
  wait(rw);  /* write */  signal(rw);
  wait(wmutex); wc--; if (wc == 0) signal(readTry); signal(wmutex);

reader:
  wait(readTry);
    wait(rmutex); rc++; if (rc == 1) wait(rw); signal(rmutex);
  signal(readTry);
  /* read */
  wait(rmutex); rc--; if (rc == 0) signal(rw); signal(rmutex);
```
**說明**：第一個寫者拿走 `readTry`，之後新讀者都卡在 `wait(readTry)`；已在讀的讀者讀完後最後一個釋放 `rw`，寫者才進入。只要不斷有寫者到達，`wc` 一直大於 0，`readTry` 不會被釋放，所以**讀者可能飢餓**（與第一型問題寫者會飢餓相對）。若要兩者都不飢餓，可以用一個公平的「排隊號誌」讓讀寫者依到達順序通過。

@q os-24 | os-vm | 3
說明 thrashing 的成因與惡性循環，並比較 working-set 模型與 page-fault frequency（PFF）兩種對策各自如何決定要給行程多少頁框、何時要暫停行程。
---
**成因**：行程分到的頁框少於它目前 locality 需要的頁數，於是不停缺頁；行程大多在等磁碟 I/O，CPU 使用率下降。若排程器看到 CPU 閒置而提高多工程度、加入更多行程，每個行程的頁框更少、缺頁更多（全域替換時還會搶別人的頁框），形成惡性循環，系統幾乎沒有進度。
**Working set**：以最近 $\Delta$ 次參考用到的相異頁數 $WSS_i$ 估計行程目前的 locality，給它至少 $WSS_i$ 個頁框。若 $D=\sum WSS_i>$ 總頁框數，就挑行程暫停（swap out），把頁框分給其他行程；有餘裕時再恢復。需要追蹤 working set（用參考位元加計時中斷近似），$\Delta$ 的選擇影響準確度。
**PFF**：直接量測每個行程的缺頁率，設上下界：高於上界就多給頁框；低於下界就收回頁框。若高於上界卻沒有空頁框，就暫停某個行程。比 working set 便宜，直接以症狀（缺頁率）調整。
兩者都是區域性的控制：保證每個執行中的行程有足夠的頁框涵蓋它的 locality。
