=== os-process
title: 行程、執行緒與 fork 語意
est: 120
recall:
- 行程的五個狀態與轉換；哪些轉換會觸發排程決策？
- fork() 回傳值；子行程繼承哪些東西、不繼承哪些？
- `fork() && fork() || fork()` 共產生幾個行程？
- 執行緒共享什麼、私有什麼？三種多執行緒模型的取捨。
- zombie 與 orphan 是什麼？
feynman: 解釋 `fork() && fork() || fork();` 執行完後總共有幾個行程（含原行程）。你要畫出行程樹，並在每個分支說明：這個行程裡 fork() 回傳什麼、&& 與 || 的短路求值讓它接下來會不會再執行下一個 fork()。最後說明如果在這行後面加一個 printf("x\n")，會印出幾個 x。
rubric:
- fork 在父行程回傳子行程 PID（非 0，視為真），在子行程回傳 0（假）
- 原行程：第一個 fork 為真，執行第二個 fork；第二個也為真，&& 為真，|| 短路，不再 fork
- 第一個 fork 的子行程：得到 0，&& 短路為假，執行第三個 fork，產生一個新行程
- 第二個 fork 的子行程：得到 0，&& 為假，執行第三個 fork，再產生一個新行程
- 共 5 個行程，每個都會執行後面的 printf，印 5 個 x
---
## 1. 行程與狀態

PCB 存：狀態、PC、暫存器、排程資訊、記憶體管理資訊（頁表基底）、I/O 狀態、開啟的檔案。

| 轉換 | 原因 |
|---|---|
| new → ready | 被允許進入（long-term scheduler） |
| ready → running | 被 dispatcher 選中 |
| running → ready | 時間片到、被更高優先權搶先（**只有可搶先排程才有**） |
| running → waiting | 等 I/O 或事件 |
| waiting → ready | I/O 完成 |
| running → terminated | exit |

> [!考點] 何時必須做排程決策
> running → waiting 與 terminate 時**一定**要選下一個（不可搶先排程只在這兩種時機）；running → ready 與 waiting → ready 時**可以**選（可搶先排程）。

Context switch 是純粹的額外負擔，時間取決於硬體（例如有多組暫存器時只要切換指標）。

## 2. fork、exec、wait

- `fork()`：父得到子的 PID，子得到 0，失敗回傳 −1。子行程**複製**父的位址空間（現代系統用 copy-on-write，寫入時才真的複製）、檔案描述子表（指向同一個開啟檔案，**共享檔案位移**）。
- 兩者的變數是各自的副本：子行程改 `x` 不影響父行程，即使印出的指標位址（虛擬位址）相同。
- `exec()` 用新程式取代整個記憶體映像，成功後**不會返回**，`exec` 之後的程式碼不執行。
- `wait()`：父行程等子行程結束並取回狀態。子行程已結束但父還沒 wait → **zombie**；父先結束 → 子成為 **orphan**，被 init／systemd 收養。

> [!陷阱] fork 與輸出緩衝
> `printf("hi"); fork();`（沒有換行）可能印出兩次 `hi`：`fork` 時 stdout 緩衝區還沒清空，被複製到子行程，兩邊結束時各自 flush。若是 `printf("hi\n")` 且輸出到終端（行緩衝）只印一次；但若輸出被導向檔案（全緩衝）還是兩次。

> [!例題] 計數
> (a) `for (i=0;i<3;i++) fork(); printf("x");` 印幾次？(b) `for (i=0;i<3;i++){ fork(); printf("x"); }` 呢？(c) `if (fork()==0) fork(); printf("x");` 呢？
+++ 看解答
(a) 迴圈結束有 $2^3=8$ 個行程，各印一次：8。(b) 第 $i$ 輪有 $2^i$ 個行程各印一次：$2+4+8=14$。(c) 父行程不進 if；子行程再 fork 一次，共 3 個行程：3。
+++

## 3. 執行緒

| 共享（同一行程內） | 各自私有 |
|---|---|
| 程式碼、全域資料、heap、開啟的檔案、signal 處理方式 | 暫存器、PC、**堆疊**、thread ID、thread-local storage |

| 模型 | 說明 | 缺點 |
|---|---|---|
| Many-to-one | 多個使用者執行緒對一個核心執行緒 | 一個執行緒做阻塞系統呼叫，整個行程卡住；無法利用多核心 |
| One-to-one（Linux、Windows） | 每個使用者執行緒一個核心執行緒 | 建立成本較高，數量受限 |
| Many-to-many | 多對多（可加 two-level） | 實作複雜 |

- 使用者層級執行緒：切換不經核心、快；核心不知道它們存在，所以不能被分到不同 CPU。
- 多執行緒程式中某執行緒呼叫 `fork()`：依系統不同，可能只複製呼叫的那個執行緒（POSIX 的 `fork`），接著 `exec` 的話這樣就夠。
- 執行緒取消：非同步（立刻）或延遲（在取消點檢查）。

## 4. 雙模式與系統呼叫

使用者程式透過 trap 進入核心模式。**特權指令**：設定計時器、清除記憶體、關閉中斷、修改裝置狀態表、直接存取 I/O。非特權：讀時鐘、發出 trap 指令（依恐龍書解答，「從使用者模式切到核心模式」也是靠 trap 發起，所以可以在使用者模式執行）。

- 中斷：硬體非同步產生；trap／exception：軟體同步產生（系統呼叫、除以零、page fault）。
- 計時器保證 OS 能拿回 CPU 控制權。
- 核心架構：單體式（效能好、難維護）、分層、**微核心**（服務在使用者空間，靠訊息傳遞，較穩定但有額外負擔）、可載入模組（Linux）。

## 5. 行程間通訊

| | 共享記憶體 | 訊息傳遞 |
|---|---|---|
| 速度 | 建立後不經核心，快 | 每次都經系統呼叫 |
| 同步 | 程式設計師自己負責 | 由核心處理 |
| 適合 | 大量資料、同一台機器 | 少量資料、分散式 |

訊息傳遞可以是阻塞（同步）或非阻塞；兩邊都阻塞稱為 rendezvous。一般 pipe 是單向、只能在有親屬關係的行程間；named pipe（FIFO）可在不相關行程間使用。

> [!陷阱] 多選題常見敘述
> - 「執行緒有自己的 heap」✗，heap 共享；堆疊才是私有。
> - 「fork 之後父子行程的變數位址相同，所以修改會互相看見」✗：虛擬位址相同，實體頁不同（COW 寫入後）。
> - 「exec 成功後會回傳 0」✗，成功就不返回。
> - 「使用者層級執行緒可以在多核心上平行執行」✗（many-to-one 時）。
> - 「context switch 越快，CPU 使用率越高」✓（其餘條件相同時）。

=== os-sched
title: CPU 排程

labs: cpu
recall:
- 寫出 FCFS、SJF、SRTF、RR、優先權各自的優缺點與「最佳於什麼」。
- SJF 預測下一次 burst 的指數平均公式；α=0 與 α=1 的意義。
- RR 時間片太大、太小各會怎樣？經驗法則是什麼？
- Rate-monotonic 的可排程充分條件；EDF 呢？
- MLFQ 的升降級規則與防止飢餓的方法。
feynman: 證明在所有行程都在時間 0 到達、不可搶先的情況下，SJF 的平均等待時間最小。推理鏈用交換論證：假設某個最佳排程中有相鄰兩個行程「長的排在短的前面」，交換它們，說明這兩個行程以外的人等待時間不變、這兩人的等待時間總和如何變化，最後推出依 burst 遞增排列最佳。
rubric:
- 任一排程中第 k 個行程的等待時間是前面所有 burst 的和
- 若相鄰兩行程 $b_i>b_j$ 且 i 在前，交換之
- 其他行程的等待時間不變（前面的集合不變）
- 這兩者的等待時間總和由 $W+(W+b_i)$ 變為 $W+(W+b_j)$，減少 $b_i-b_j>0$
- 反覆交換（像泡沫排序）得到依 burst 遞增的排程，平均等待時間最小；等價寫法：總等待 = $\sum (n-k)b_{(k)}$，大的 burst 乘上小的係數

## 1. 衡量標準

CPU 使用率、throughput（單位時間完成數）、**周轉時間**（完成 − 到達）、**等待時間**（在 ready queue 的總時間 = 周轉 − burst，不計 I/O）、**回應時間**（第一次拿到 CPU − 到達）。

## 2. 演算法比較

| 演算法 | 搶先 | 特性 | 問題 |
|---|---|---|---|
| FCFS | 否 | 簡單 | **Convoy effect**：短工作卡在長工作後面 |
| SJF | 否 | 平均等待時間最小（同時到達、不可搶先時） | 要預測 burst；長工作可能飢餓 |
| SRTF | 是 | 平均等待時間最小（可搶先時） | 頻繁 context switch；飢餓 |
| 優先權 | 皆可 | 依重要性 | 飢餓 → **aging** |
| RR | 是 | 回應時間好，分時系統 | 平均周轉通常比 SJF 差 |
| MLQ | — | 依類別分佇列，佇列間固定優先或分時間比例 | 行程不能換佇列 |
| MLFQ | 是 | 用完時間片就降級，等待太久就升級 | 參數多 |

@lab cpu

> [!考點] RR 的時間片 $q$
> $q\to\infty$ 時退化成 FCFS；$q$ 太小則 context switch 比例變高（$q$ 應遠大於切換時間）。經驗法則：約 80% 的 CPU burst 應該小於 $q$。周轉時間**不一定**隨 $q$ 增加而改善（不單調）。

**預測下一個 burst**：$\tau_{n+1}=\alpha t_n+(1-\alpha)\tau_n$，展開後過去第 $j$ 次的權重是 $\alpha(1-\alpha)^j$。$\alpha=0$：只看初始預測；$\alpha=1$：只看最近一次。

> [!例題] 指數平均
> $\alpha=1/2$，$\tau_0=10$，實際 burst 依序 6、4、6、4。求 $\tau_4$。
+++ 看解答
$\tau_1=8$、$\tau_2=6$、$\tau_3=6$、$\tau_4=5$。
+++

## 3. 即時排程

週期性工作 $i$：週期 $p_i$、執行時間 $t_i$，使用率 $U=\sum t_i/p_i$。

| 演算法 | 優先權 | 可排程條件 |
|---|---|---|
| Rate-monotonic（RM） | 靜態，週期越短越優先 | **充分**條件 $U\le n(2^{1/n}-1)$（$n=1$:1、$n=2$:0.828、$n\to\infty$:$\ln2\approx0.693$）；超過不一定失敗，要畫時間軸驗證 |
| EDF | 動態，截止時間越早越優先 | $U\le1$ 為**充要**條件（可搶先、截止＝週期） |

> [!例題] RM 失敗、EDF 成功
> $P_1$：$p=50,t=25$；$P_2$：$p=80,t=35$。
+++ 看解答
$U=0.5+0.4375=0.9375>0.828$。RM：$P_1$ 跑 0–25，$P_2$ 跑 25–50，$P_1$ 在 50 搶回跑到 75，$P_2$ 剩 10 在 75–85 才完成，錯過 80 的截止。EDF：$U\le1$ 所以一定可排程；在 50 時 $P_2$ 截止 80 比 $P_1$ 的 100 早，$P_2$ 繼續跑到 60 完成。
+++

## 4. 多處理器與實務

- 處理器親和性（affinity）：避免 cache 失效；soft／hard affinity。
- 負載平衡：push migration、pull migration；和親和性互相拉扯。
- Linux CFS：每個任務有 vruntime（依 nice 值加權），用紅黑樹挑 vruntime 最小的，$O(\lg n)$。
- **Little 公式**：$n=\lambda\times W$（佇列平均長度＝到達率×平均等待時間）。

> [!陷阱] 多選題常見敘述
> - 「SJF 在任何情況下平均周轉時間最小」✗：要「同時到達」或改用 SRTF；而且需要知道 burst。
> - 「RR 一定不會飢餓」✓（每個行程在 $(n-1)q$ 內一定輪到）。
> - 「優先權排程一定是可搶先的」✗。
> - 「FCFS 的平均等待時間與到達順序無關」✗。
> - 「I/O-bound 行程應該給較高優先權」通常 ✓，讓 I/O 裝置保持忙碌。

=== os-sync
title: 同步：臨界區、Peterson、號誌與監視器

recall:

- 只用 turn、只用 flag 的兩種錯誤解法分別違反哪一條？
- Peterson 的程式碼；為什麼在現代處理器上可能失效？
- Bounded buffer 中 wait(mutex) 與 wait(empty) 對調會怎樣？
- Hoare 與 Mesa 語意的監視器差在哪裡？為什麼 Mesa 要用 while？
- 什麼是 priority inversion？怎麼解？
feynman: 證明 Peterson 演算法滿足互斥（mutual exclusion）與有限等待（bounded waiting）。互斥用反證：假設兩個行程同時在臨界區，從 flag 與 turn 的值推出矛盾，要說清楚「最後寫 turn 的是誰」這個關鍵。有限等待要說明 P_i 在 while 迴圈等待時，P_j 最多再進入臨界區幾次、為什麼。
rubric:
- 寫出 $P_i$ 的進入區：flag[i]=true; turn=j; while(flag[j] && turn==j);
- 互斥：若兩者都在 CS，則 flag[0]=flag[1]=true，兩人的 while 條件都已不成立，表示 turn 必須同時是 0 與 1
- 更精確：較晚寫入 turn 的那個行程（例如 $P_i$ 寫 turn=j）會看到 flag[j]==true 且 turn==j 而卡住，矛盾
- 有限等待：$P_j$ 離開後若想再進入，會先設 turn=i，於是 $P_j$ 自己被擋，$P_i$ 可以進入
- 所以 $P_i$ 最多等 $P_j$ 進入一次（bounded by 1）；progress 同理：沒人在 CS 時不會兩人一起卡住
---
## 1. 三個條件

1. **互斥**：同時最多一個行程在臨界區。
2. **Progress**：沒人在臨界區時，只有想進入的行程參與決定誰進入，而且決定不能無限延後。
3. **Bounded waiting**：一個行程提出請求後，其他行程搶先進入的次數有上限。

> [!考點] 兩個錯誤解法
> - 只用 `turn`（嚴格輪流）：滿足互斥，**違反 progress**——$P_0$ 不想進入時，$P_1$ 連續第二次就進不去。
> - 只用 `flag`（先舉旗再看對方）：兩人同時舉旗 → 互相等待，**違反 progress**（死結）；若改成「先看對方再舉旗」則**違反互斥**。

## 2. Peterson 演算法

```c
// P_i, j = 1 - i
flag[i] = true;
turn = j;                       // 禮讓
while (flag[j] && turn == j) ;  // busy wait
/* critical section */
flag[i] = false;
```

三個條件都滿足，但**只限兩個行程**，而且假設讀寫不會被重排。現代處理器或編譯器可能把 `flag[i]=true` 與讀 `flag[j]` 重排，兩人都看到對方是 false 而同時進入，需要 **memory barrier**。

n 個行程：**Bakery 演算法**（拿號碼牌，號碼相同比 PID）。

## 3. 硬體支援

- `test_and_set(&lock)`：原子地讀出舊值並設為 true。簡單版滿足互斥但**不滿足 bounded waiting**；加上 `waiting[]` 陣列、離開時從 $i+1$ 起循環找下一個等待者交棒，就能保證等待 $\le n-1$ 輪。
- `compare_and_swap(&v, expected, new)`：用來實作無鎖結構與原子變數。
- 關中斷只在單處理器可行，多處理器上太慢且不安全。

## 4. 號誌（Semaphore）

```c
wait(S)  { S.value--; if (S.value < 0) { 加入 S.list; block(); } }
signal(S){ S.value++; if (S.value <= 0) { 從 S.list 移出 P; wakeup(P); } }
```

值為負時，絕對值等於等待中的行程數。`wait`／`signal` 本身必須是原子的（內部用短暫的 spinlock）。

> [!例題] 用號誌強制順序
> 要求 $P_1$ 的 S1 先於 $P_2$ 的 S2：`synch` 初值 0；$P_1$：`S1; signal(synch);`；$P_2$：`wait(synch); S2;`。

### 經典問題

**Bounded buffer**（`mutex=1, empty=n, full=0`）：
```c
producer: wait(empty); wait(mutex); 放入; signal(mutex); signal(full);
consumer: wait(full);  wait(mutex); 取出; signal(mutex); signal(empty);
```
若生產者改成先 `wait(mutex)` 再 `wait(empty)`：緩衝區滿時它拿著 mutex 睡在 empty 上，消費者拿不到 mutex 無法取出 → **死結**。（兩個 signal 對調則無妨。）

**Readers–writers（第一型，讀者優先）**：`rw_mutex=1, mutex=1, read_count=0`。第一個讀者 `wait(rw_mutex)`，最後一個讀者 `signal(rw_mutex)`。寫者可能**飢餓**；第二型（寫者優先）則讀者可能飢餓。

**Dining philosophers**：每人先拿左筷再拿右筷 → 可能死結。解法：最多 4 人同時上桌；兩支筷子一起拿（在臨界區內檢查）；奇數號先左、偶數號先右（打破環狀等待）。這些解法不一定防止飢餓。

## 5. 監視器（Monitor）

一次只有一個行程在監視器內執行。條件變數 `x.wait()` 讓呼叫者睡覺並**釋放監視器**；`x.signal()` 喚醒一個等待者，**沒人等待時沒有任何效果**（和號誌不同，號誌的 signal 會被記住）。

| 語意 | 被喚醒者 | 發出 signal 者 | 程式寫法 |
|---|---|---|---|
| Hoare（signal-and-wait） | 立刻執行 | 等待 | `if (!cond) x.wait();` |
| Mesa（signal-and-continue） | 之後才執行，條件可能又被改 | 繼續 | **`while (!cond) x.wait();`** |

## 6. 活性問題

- **Priority inversion**：低優先權 L 持有鎖，高優先權 H 等它，中優先權 M 一直搶占 L，結果 H 被 M 間接卡住。解法 **priority inheritance**：L 持鎖期間暫時繼承 H 的優先權（火星探路者號事件）。
- Spinlock：忙等，適合多核心且臨界區很短（短於兩次 context switch）；單核心上無意義。

> [!陷阱] 多選題常見敘述
> - 「binary semaphore 與 mutex lock 完全相同」✗：mutex 有擁有者概念（誰 lock 誰 unlock），semaphore 沒有。
> - 「Peterson 可以直接用在多核心處理器」✗（記憶體重排）。
> - 「monitor 的 signal 在沒有人等待時會被保留」✗。
> - 「死結一定代表飢餓」✓；「飢餓一定代表死結」✗。
> - 「所有號誌操作都會造成忙等」✗：用等待佇列實作的不會。

=== os-deadlock
title: 死結
est: 110
labs: banker
recall:
- 死結的四個必要條件。
- 資源配置圖有環：何時一定死結、何時不一定？
- 安全狀態、不安全狀態、死結三者的關係。
- Banker 演算法的資料結構與時間複雜度。
- n 個行程各最多需要 k 個同類資源，系統至少要幾個資源才不會死結？
feynman: 證明「替所有資源類型定一個全序，規定每個行程只能依遞增順序申請資源」可以防止死結。推理鏈用反證：假設仍有一個循環等待 P0→P1→…→Pn→P0，寫出每個行程持有的資源與它在等的資源之間的順序關係，串起來得到矛盾。並說明這是打破四個必要條件中的哪一個。
rubric:
- 設資源有全序函數 F，每個行程持有資源後只能申請 F 更大的資源
- 假設循環等待：$P_i$ 持有 $R_i$、等待 $P_{i+1}$ 持有的 $R_{i+1}$
- 因為 $P_i$ 持有 $R_i$ 時才申請 $R_{i+1}$，所以 $F(R_i)<F(R_{i+1})$
- 串起來 $F(R_0)<F(R_1)<\dots<F(R_n)<F(R_0)$，矛盾
- 這打破的是「循環等待」條件
---
## 1. 四個必要條件（同時成立才可能死結）

1. **互斥**：資源一次只能被一個行程使用。
2. **持有並等待**（hold and wait）。
3. **不可搶占**。
4. **循環等待**。

資源配置圖（RAG）：有環是死結的**必要**條件；若每類資源只有**一個實例**，有環就是**充分**條件。多實例時有環不一定死結。

## 2. 處理方式

| 方式 | 做法 | 代價 |
|---|---|---|
| 預防 | 打破任一必要條件：例如一次申請全部資源（破持有並等待）、資源排序（破循環等待） | 資源使用率低、可能飢餓 |
| 避免 | 每次配置前確認仍處於**安全狀態**（Banker） | 要事先知道最大需求；$O(mn^2)$ |
| 偵測與復原 | 允許死結，定期偵測（單實例用 wait-for graph 找環 $O(n^2)$；多實例用類 Banker 演算法），再終止或搶占 | 偵測成本、復原代價 |
| 忽略 | 鴕鳥演算法（多數通用 OS） | — |

> [!考點] 安全狀態
> 安全 ⇒ 不會死結；**不安全不一定死結**（只是 OS 無法保證，行程可能不會真的要到最大需求）；死結 ⊂ 不安全。

## 3. Banker 演算法

$n$ 個行程、$m$ 類資源：`Available[m]`、`Max[n][m]`、`Allocation[n][m]`、`Need = Max − Allocation`。

- **安全演算法**：`Work = Available`；反覆找 `Finish[i]==false` 且 `Need[i] ≤ Work` 的 $i$，令 `Work += Allocation[i]`、`Finish[i]=true`。全部完成即安全。$O(m\cdot n^2)$。
- **請求演算法**：先檢查 `Request ≤ Need`（否則錯誤）、`Request ≤ Available`（否則等待），再假裝配置並執行安全演算法，安全才真的配置。

@lab banker

> [!例題] 至少需要幾個資源
> $n$ 個行程，每個最多同時需要 $k$ 個同類資源，系統有 $m$ 個。保證不死結的條件？
+++ 看解答
最壞情況是每個行程都拿到 $k-1$ 個、都在等最後一個。只要再多 1 個，某行程就能完成並釋放。所以 $m\ge n(k-1)+1$。一般化：最大需求各為 $k_i$ 時，$m\ge\sum(k_i-1)+1$，即 $\sum k_i<m+n$。
+++

## 4. 復原

- 終止全部死結行程，或一次終止一個直到解除（每次都要重新偵測）。
- 搶占資源：選犧牲者（成本最小）、**rollback**、避免同一個行程一再被選（飢餓）。

> [!陷阱] 多選題常見敘述
> - 「RAG 有環就一定死結」✗（多實例）。
> - 「系統處於不安全狀態就一定死結」✗。
> - 「Banker 演算法可以用在行程最大需求未知的系統」✗。
> - 「破壞互斥條件是最常用的預防法」✗：很多資源本質就不可共享（印表機、鎖）。
> - **Livelock**：行程沒有阻塞、一直在改變狀態，卻都沒有進展（例如兩人一直互相讓路）。

=== os-memory
title: 主記憶體：分頁、分段與頁表結構
est: 150
recall:
- 位址繫結的三個時機；什麼時候邏輯位址與實體位址不同？
- First／best／worst fit 的比較；50% 規則說什麼？
- 有 TLB 時的有效存取時間怎麼算？
- 多層頁表、雜湊頁表、反轉頁表各解決什麼問題？反轉頁表的缺點？
- 分段與分頁各會造成哪種碎片？
feynman: 解釋為什麼 32 位元位址、4 KB 頁、4 bytes PTE 的系統要用兩層頁表，以及兩層頁表在什麼情況下能省記憶體、什麼情況下反而更多。推理鏈要算出單層頁表的大小、說明它必須連續且常駐的問題、把 VPN 切成 10/10 後外層頁表的大小，再以一個只用到程式碼區與堆疊區的稀疏位址空間為例算出實際用量。
rubric:
- 單層：VPN 20 位元 → $2^{20}$ 個 PTE × 4 B = 4 MB，每個行程都要一份，且要連續
- 兩層：外層 $2^{10}$ 項 × 4 B = 4 KB 剛好一頁；每個內層頁表也是一頁，管 4 MB 的位址空間
- 稀疏位址空間（例如只用頂端與底端各幾 MB）只需配置用到的內層頁表，例如 1 外層 + 2 內層 = 12 KB
- 若整個位址空間都被用到，兩層總共 4 MB + 4 KB，反而略多
- 代價：每次轉換多一次記憶體存取，所以需要 TLB
---
## 1. 位址繫結

- 編譯時期（absolute code）、載入時期（relocatable code）：邏輯位址＝實體位址。
- **執行時期**：需要 MMU，邏輯（虛擬）位址 ≠ 實體位址，行程可以在執行中被搬移。最簡單的 MMU：relocation（base）暫存器＋limit 暫存器。

## 2. 連續配置

| 策略 | 說明 | 評價 |
|---|---|---|
| First-fit | 第一個夠大的洞 | 快；模擬顯示與 best-fit 利用率相近 |
| Best-fit | 最小的夠大的洞 | 要搜尋全部（除非排序），留下很小的碎洞 |
| Worst-fit | 最大的洞 | 通常最差 |

**外部碎片**：總空間夠但不連續。**50% 規則**：first-fit 下，配置 $N$ 個區塊時約有 $0.5N$ 個區塊因碎片浪費，即約 1/3 的記憶體不能用。解法：compaction（需執行時期繫結）、分頁、分段。

## 3. 分頁

邏輯位址 $m$ 位元、頁大小 $2^n$：頁號 $m-n$ 位元、位移 $n$ 位元。**沒有外部碎片**，但有**內部碎片**（平均每個行程最後一頁浪費半頁）。

- 頁表放在記憶體，PTBR 指向它；每次存取都要多一次記憶體存取 → 用 **TLB**（關聯式記憶體，可存 ASID 避免每次 context switch 清空）。
- 有效存取時間（TLB 查詢 $\varepsilon$、記憶體 $m$、命中率 $h$、單層頁表）：
$$EAT=h(\varepsilon+m)+(1-h)(\varepsilon+2m)$$
$k$ 層頁表時失誤要 $\varepsilon+(k+1)m$。（若題目說 TLB 與記憶體同時查，命中時就不加 $\varepsilon$，要看清楚。）
- valid-invalid 位元、保護位元（唯讀）；**共享頁**：可重入（reentrant，不會自我修改）的程式碼可以讓多個行程的頁表指到同一個頁框。

## 4. 頁表結構

| 結構 | 想法 | 適用／缺點 |
|---|---|---|
| 多層（hierarchical） | 把 VPN 切段，只配置用到的內層頁表 | 64 位元時層數太多 |
| 雜湊頁表 | 以 VPN 雜湊，碰撞用鏈結；clustered 版每項對應多頁 | 適合 > 32 位元的稀疏位址空間 |
| 反轉頁表 | 全系統一張表，**每個實體頁框一項**（存 PID＋VPN） | 表的大小只與實體記憶體成正比；查詢要搜尋（配合雜湊）；**共享記憶體難做**（一個頁框只能對應一個虛擬位址） |

> [!例題] 頁表大小
> 64 位元虛擬位址、8 KB 頁、PTE 8 bytes，若每一層頁表都要剛好放進一頁，需要幾層？
+++ 看解答
offset 13 位元，VPN 51 位元。一頁放 $2^{13}/2^3=2^{10}$ 個 PTE，每層吃 10 位元，$\lceil51/10\rceil=6$ 層。這就是為什麼 64 位元系統改用雜湊或反轉頁表，或只用 48 位元虛擬位址（x86-64 用 4 層 × 9 位元 + 12 位元 offset）。
+++

## 5. 分段

邏輯位址＝（段號, 位移）；段表存 base 與 limit，位移超過 limit 就 trap。符合使用者對程式的看法（程式碼、資料、堆疊各一段），容易做保護與共享，但有**外部碎片**。IA-32 是分段＋分頁。

> [!陷阱] 多選題常見敘述
> - 「分頁完全沒有碎片」✗，有內部碎片。
> - 「頁越大，內部碎片越小」✗，越大。頁大好處：頁表小、TLB reach 大、I/O 效率好。
> - 「TLB 失誤一定會造成 page fault」✗：只要查頁表；PTE 無效才是 page fault。
> - 「反轉頁表能讓每個行程擁有自己的頁表」✗，全系統一張。
> - 「swap 出去的行程回來時一定要放回原來的實體位址」✗（執行時期繫結時）。

=== os-vm
title: 虛擬記憶體：需求分頁、頁替換與 thrashing
est: 170
labs: page
recall:
- 處理 page fault 的步驟。
- 含 page fault 的 EAT 公式；為什麼缺頁率要極低？
- Belady 異常；哪類演算法保證不會發生？
- LRU 的兩種精確實作與近似演算法（clock、enhanced second chance）。
- Thrashing 的成因；working set 與 PFF 如何解決？
- 二維陣列依列或依行走訪的缺頁數為何差很多？
feynman: 解釋為什麼 LRU 永遠不會發生 Belady 異常，但 FIFO 會。推理鏈要定義「堆疊演算法」（n 個頁框時在記憶體中的頁面集合，永遠是 n+1 個頁框時的子集合），證明 LRU 符合（記憶體中就是最近用過的 n 個不同頁），並說明有了這個包含關係為什麼缺頁數不會隨頁框增加而變多；最後用 FIFO 的反例說明包含關係如何被打破。
rubric:
- 定義堆疊演算法：任一時刻 $M(n,t)\subseteq M(n+1,t)$
- LRU：$M(n,t)$ 是最近使用的 n 個相異頁，必然包含於最近 n+1 個
- 若某次參考在 n+1 頁框時缺頁，則該頁不在 $M(n+1,t)$，也就不在 $M(n,t)$，n 頁框時也缺頁
- 所以缺頁數隨頁框數單調不增
- FIFO 的集合取決於載入時間，不滿足包含（1 2 3 4 1 2 5 1 2 3 4 5：3 頁框 9 次、4 頁框 10 次）
---
## 1. 需求分頁

Page fault 處理：(1) trap 到 OS；(2) 檢查參考是否合法，不合法就終止；(3) 找空頁框（沒有就跑替換演算法）；(4) 排程磁碟讀入；(5) 讀完更新頁表、valid=1；(6) **重新執行**造成 fault 的那條指令。

$$EAT=(1-p)\times ma+p\times\text{page fault time}$$

$ma=200$ ns、處理缺頁 8 ms 時，要讓變慢不超過 10%，$p<2.5\times10^{-6}$（約 40 萬次存取才能有一次缺頁）。

- **Copy-on-write**：fork 後父子共享頁面，標為唯讀，寫入時才複製。
- **Dirty（modify）bit**：被換出的頁若沒被改過不用寫回，換頁成本減半。

## 2. 頁替換

| 演算法 | 換出 | 性質 |
|---|---|---|
| FIFO | 最早載入 | 可能 **Belady 異常** |
| OPT | 未來最晚才用到 | 最佳，需要未來資訊，作為比較基準 |
| LRU | 最久沒用 | 堆疊演算法；實作：每次存取記時間（counter）或用堆疊（雙向鏈結移到頂） |
| Second chance（clock） | 參考位元為 0 者；為 1 則清 0 並給第二次機會 | LRU 近似；全部為 1 時退化成 FIFO |
| Enhanced second chance | 依 (ref, modify) 分四類，優先換 (0,0) | 減少寫回 |
| LFU／MFU | 次數最少／最多 | 不常用 |

@lab page

> [!考點] 恐龍書標準例題
> 參考串 `7 0 1 2 0 3 0 4 2 3 0 3 2 1 2 0 1 7 0 1`、3 個頁框：FIFO 15 次、LRU 12 次、OPT 9 次。上面的動畫可以逐步驗證。

## 3. 頁框配置與 thrashing

- 配置：平均分配、依行程大小**比例**分配、依優先權。每個行程有**最少頁框數**，由指令集決定（一條指令可能碰到的頁數）。
- **全域替換**：可從別的行程搶頁框，throughput 較好但行程的缺頁率受別人影響；**區域替換**：只從自己的頁框中選。
- **Thrashing**：行程的頁框少於它正在使用的頁（locality），一直缺頁、一直等 I/O → CPU 使用率下降 → 系統以為負載不足又加入更多行程 → 更糟。
- **Working set**：$WSS_i$＝最近 $\Delta$ 次參考用到的相異頁數；$D=\sum WSS_i$。若 $D>$ 總頁框數就暫停某些行程。$\Delta$ 太小抓不到 locality，太大會跨好幾個 locality。
- **Page-fault frequency**：缺頁率高於上限就給更多頁框，低於下限就拿走。

## 4. 其他考量

- **TLB reach**＝TLB 項數 × 頁大小。用大頁（huge page）擴大 reach。
- **程式結構**：`int data[128][128]`，頁大小 128 個 int（一列一頁），頁框少於 128 個。依行走訪（內層迴圈跑列索引）每次存取都換一頁：$128\times128=16384$ 次缺頁；依列走訪：128 次。
- **Prepaging**：預先載入可能用到的頁，若用到的比例 $\alpha$ 夠高才划算。
- **I/O interlock**：正在做 DMA 的頁要鎖住（lock bit），不能被換出。
- 核心記憶體配置：**buddy system**（2 的冪次切分與合併，有內部碎片）、**slab**（每類核心物件一個快取，沒有碎片、配置快）。

> [!陷阱] 多選題常見敘述
> - 「頁框越多，缺頁越少」✗（FIFO 有 Belady 異常）；對 LRU、OPT ✓。
> - 「LRU 會有 Belady 異常」✗。
> - 「增加多工程度一定提高 CPU 使用率」✗（thrashing）。
> - 「working set 模型需要知道未來的參考」✗，看的是過去 $\Delta$ 次。
> - 「clock 演算法就是 LRU」✗，是近似。

## 2. RAID

| 等級 | 方式 | 可用容量（n 顆） | 容錯 | 小寫入 |
|---|---|---|---|---|
| 0 | 條帶化 | $n$ | 無 | 1 次寫 |
| 1 | 鏡像 | $n/2$ | 每組壞 1 顆 | 2 次寫 |
| 5 | 分散式同位元 | $n-1$ | 1 顆 | 4 次 I/O（讀舊資料、讀舊同位元、寫新資料、寫新同位元） |
| 6 | 兩組同位元（P+Q） | $n-2$ | 2 顆 | 6 次 I/O |
| 1+0 | 先鏡像再條帶 | $n/2$ | 每個鏡像組壞 1 顆都可以 | |
| 0+1 | 先條帶再鏡像 | $n/2$ | 一顆壞就讓整邊失效 | |

RAID 4 的同位元集中在一顆磁碟，小寫入時它成為瓶頸；RAID 5 把同位元分散解決這點。**RAID 1+0 比 0+1 可靠**。

## 3. 檔案配置

| 方式 | 循序存取 | 隨機存取 | 問題 |
|---|---|---|---|
| 連續 | 快 | $O(1)$ | 外部碎片、檔案難長大（用 extent 緩解） |
| 鏈結 | 可 | 要走 $i$ 個區塊 | 指標佔空間、一個指標壞掉後面全丟；**FAT** 把鏈結放在表裡，可快取 |
| 索引 | 可 | 讀索引後 $O(1)$ | 索引區塊的額外空間；大檔案用多層（Unix inode） |

## 4. 空閒空間、目錄與連結

- **Bitmap**：磁碟 1 TB、區塊 4 KB → $2^{28}$ 個區塊 → bitmap 32 MB。容易找連續空間。
- 鏈結串列、grouping（第一個空區塊存 $n$ 個空區塊位址）、counting（起點＋長度）。
- **Hard link**：另一個目錄項指向同一個 inode，inode 有參考計數，計數為 0 才真的刪除；不能跨檔案系統、通常不能連到目錄。**Symbolic link**：一個存路徑的特殊檔案，可跨檔案系統，原檔刪除後變成懸空連結。
- 開檔：系統層級的 open-file table（位置、計數）與行程層級的表（檔案位移、存取模式）。

## 5. 一致性與日誌

- 一致性檢查（fsck）：比對目錄結構與區塊配置，很慢。
- **Journaling**（日誌式）：metadata 的變更先以 transaction 寫進循環日誌，commit 後再套用；當機後只需重放已 commit 的交易。
- Log-structured FS：所有寫入都以追加方式進行。

> [!陷阱] 多選題常見敘述
> - 「SSTF 是最佳的磁碟排程」✗，也可能飢餓。
> - 「RAID 1 的讀取效能比單一磁碟差」✗，可以從兩顆讀。
> - 「RAID 5 可以容忍兩顆磁碟同時故障」✗，那是 RAID 6。
> - 「刪除 hard link 的原始檔名後，資料就消失」✗，還有其他連結時資料仍在。
> - 「SSD 也應該使用 SCAN 排程」✗。
