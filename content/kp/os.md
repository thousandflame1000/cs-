=== os-process#1
title: 行程與五種狀態
mins: 35
goal: 分得清程式和行程；會畫五狀態圖、說出每個轉換的原因；知道 PCB 存什麼、context switch 是什麼
---
> [!先記住]
> **行程（process）**＝正在執行的程式，加上它的狀態（暫存器、記憶體、開的檔案）。作業系統用一個 **PCB** 記錄每個行程的資料。行程在五個狀態之間跳來跳去。

```fig
flow: 新建 -> 就緒 -> 執行* -> 結束
flow: 執行 -> 等 I/O：等待 -> I/O 好了：回到就緒
cap: 時間片用完時，執行 → 就緒；被排程器選中時，就緒 → 執行
```

**程式**是磁碟上的檔案；**行程**（process）是**正在跑的程式**：有自己的記憶體、目前跑到哪一行（PC）、暫存器的值、開啟的檔案。同一個程式開兩次，就是兩個行程。

OS 為每個行程準備一張「資料卡」，叫 **PCB**（Process Control Block），記錄：狀態、PC、暫存器、排程資訊、記憶體資訊、開啟的檔案。

?? 選擇 | 同一個瀏覽器程式開了三個視窗（各自獨立的行程），有幾個 PCB？
[ ] 1
[x] 3
[ ] 0
!! 每個行程一張資料卡。
>> 三個行程、三個 PCB；程式檔只有一個。

行程一生有五種**狀態**：
- **new**：剛建立
- **ready**：準備好了，排隊等 CPU
- **running**：正在 CPU 上跑
- **waiting**：在等某件事（例如等 I/O、等鍵盤輸入）
- **terminated**：結束

一顆 CPU 同時只有**一個** running，其他都在 ready 或 waiting 的佇列裡。

?? 選擇 | 一個行程在等使用者按鍵盤，它在哪個狀態？
[ ] ready
[x] waiting
[ ] running
!! 給它 CPU 它能做事嗎？
>> 它在等事件，給它 CPU 也沒用，所以是 waiting；按下鍵之後才回到 ready。

| 轉換 | 原因 |
|---|---|
| ready → running | 被排程器選中 |
| running → ready | 時間片用完、被搶先 |
| running → waiting | 要等 I/O 或事件 |
| waiting → ready | 等的事情發生了 |
| running → terminated | 結束 |

注意：**waiting 不能直接變 running**，要先回 ready 排隊。

?? 排序 | 一個行程讀檔案的過程，狀態依序是？
- running（執行到讀檔指令）
- waiting（等磁碟）
- ready（磁碟讀完，排隊等 CPU）
- running（又輪到它）
!! waiting 結束後能直接跑嗎？
>> waiting → ready → running，中間一定要排隊。

**Context switch**：CPU 從行程 A 換到行程 B 時，把 A 的狀態（PC、暫存器）存進 A 的 PCB，再從 B 的 PCB 載入。這段時間 CPU 沒在做有用的事，是**純負擔**。

**什麼時候 OS 一定要選下一個行程？** running → waiting、running → terminated 時（CPU 空了）。running → ready、waiting → ready 時「可以」換人——會這樣做的叫**可搶先**排程。

?? 選擇 | 哪一個轉換只有「可搶先」的排程才會發生？
[ ] running → waiting
[x] running → ready
[ ] running → terminated
!! 哪一個是「行程還想跑，卻被拿走 CPU」？
>> running → ready 是被搶走（時間到或有更重要的來）；另外兩個是行程自己讓出 CPU。

@例題 一顆 CPU、三個行程 A、B、C。A 正在跑，B 在 ready 佇列，C 在等磁碟。接著發生：A 要讀鍵盤；C 的磁碟讀完；OS 選了 B。寫出每一步後三個行程的狀態。
@寫 A 要讀鍵盤之後 | A：waiting；B：ready；C：waiting。CPU 空了，OS 必須選下一個。
@寫 C 的磁碟讀完之後 | C：waiting → ready。現在 ready 佇列有 B、C。
@步 OS 選了 B | B：running；C：ready；A：waiting。
@答 最後 A waiting、B running、C ready。

=== os-process#2
title: fork、exec、wait：建立行程
mins: 40
goal: 會算 fork 之後有幾個行程、印幾次；知道 fork 回傳值、exec 不會返回、zombie 和 orphan
---
> [!先記住]
> **fork()** 把目前的行程複製一份。之後兩個行程從同一行繼續跑，唯一的差別是回傳值：**父行程拿到子行程的 PID，子行程拿到 0**。**exec()** 把自己換成另一個程式；**wait()** 讓父行程等子行程結束。

```fig
flow: fork() -> 父行程：拿到子的 PID | 子行程：拿到 0 -> 兩個都從下一行繼續*
```

`fork()` 會把呼叫它的行程**整個複製一份**。複製出來的叫**子行程**，原本的叫**父行程**。兩個都從 fork 的**下一行**繼續跑。

怎麼分誰是誰？看回傳值：
- 父行程拿到**子行程的 PID**（一個正數）
- 子行程拿到 **0**
- 失敗回傳 −1

?? 選擇 | `pid = fork();` 之後，子行程裡 `pid` 是多少？
[x] 0
[ ] 子行程自己的 PID
[ ] 父行程的 PID
!! 父、子拿到的回傳值不一樣。
>> 子行程拿到 0，父行程拿到子的 PID。

先看影片：fork 到底複製了什麼，三次 fork 有幾個行程。

@影片 os-process 0-83.1

**計數規則**：每呼叫一次 fork，「當時存在的每個行程」都會分裂成兩個。
`for (i = 0; i < 3; i++) fork();` → $1\to2\to4\to8$，最後 8 個行程。

?? 填空 | `fork(); fork();` 之後總共有幾個行程（包含原本的）？
== 4
!! 第一次 fork 後有 2 個，第二次每個都再分裂。
>> $2\times2=4$。

印幾次要看 printf 在哪：
- `for (i<3) fork(); printf("x");`：8 個行程各印一次，**8 次**
- `for (i<3) { fork(); printf("x"); }`：第 $i$ 輪有 $2^i$ 個行程各印一次，$2+4+8=$ **14 次**

?? 填空 | `if (fork() == 0) fork(); printf("x");` 印幾次 x？
== 3
!! 父行程拿到正數，不進 if；子行程拿到 0，再 fork 一次。
>> 父 1 個、子 1 個、子的子 1 個，共 3 個行程各印一次。

再看影片：`fork() && fork() || fork()` 有幾個行程，還有變數是不是共用。

@影片 os-process 83.2-149.3

?? 選擇 | `fork() && fork();` 之後總共有幾個行程（包含原本的）？
[x] 3
[ ] 4
[ ] 2
!! 第一個 fork 的子行程拿到 0，`&&` 會不會讓它跑第二個 fork？
>> 原本的行程跑兩個 fork（生 2 個），第一個 fork 的子行程拿到 0，`&&` 短路，不再 fork：$1+2=3$。

**變數各一份**：fork 之後父、子的記憶體是**各自的副本**。子行程改 `x`，父行程看不到（就算印出來的位址一樣，那是虛擬位址）。現代系統用 **copy-on-write**：一開始共用，誰要寫才真的複製。

**exec**：用另一個程式**取代**自己整個記憶體。成功後**不會返回**，exec 後面的程式碼不會執行。常見用法：fork 之後，子行程 exec 新程式。

**wait**：父行程等子行程結束。子結束了但父還沒 wait → **zombie**（殭屍）；父先結束 → 子變 **orphan**（孤兒），被 init 收養。

?? 選擇 | `execlp("ls", ...)` 成功之後，下一行的 `printf("done")` 會執行嗎？
[x] 不會
[ ] 會
!! exec 成功會不會回到原本的程式？
>> 記憶體已經換成 ls 了，原本的程式碼不在了；只有 exec 失敗時才會執行下一行。

最後一段影片：考試陷阱。

@影片 os-process 149.4-179.4

?? 寫 | 在手寫板畫出 `fork(); fork();` 的行程樹（誰生了誰），並標出總共幾個行程。
== 原本 P 第一次 fork 生出 C1；接著 P 和 C1 各再 fork：P 生 C2、C1 生 C3。共 4 個。
!! 第二次 fork 時已經有兩個行程。
>> 畫樹最不容易數錯：每一層的每個行程都往下分叉。

@例題 下面的程式結束後，父行程印出的 `x` 是多少？子行程印的呢？
```
int x = 5;
if (fork() == 0) { x = x + 10; printf("%d", x); }
else { wait(NULL); x = x - 1; printf("%d", x); }
```
@寫 子行程走哪一邊？印什麼？ | 子拿到 0，進 if：$x=15$，印 15。
@寫 父行程走哪一邊？它的 x 是幾？ | 父進 else，等子結束；父的 $x$ 還是 5（子改的是自己的副本），$x=4$，印 4。
@步 印出順序 | 父有 wait，所以先印子的 15，再印父的 4。
@答 子印 15、父印 4，輸出 `154`。

=== os-process#3
title: 執行緒：同一個行程裡的好幾條工作線
mins: 35
goal: 分得清執行緒共享什麼、私有什麼；比較使用者層級和核心層級執行緒；認得三種對應模型
---
> [!先記住]
> **執行緒（thread）**：同一個行程裡可以同時跑的好幾條執行路線。它們**共用**程式碼、全域資料、heap 和檔案，但**各自有**暫存器、PC 和堆疊。開執行緒比開行程便宜很多。

```fig
array
row 共用: 程式碼 全域 heap 檔案
row 各自: 暫存器* PC* 堆疊*
cap: 同一個行程的每個執行緒
```

**執行緒**（thread）：一個行程裡面可以有好幾條**同時跑的工作線**。例如瀏覽器一條執行緒畫畫面、一條下載。

同一個行程的執行緒：
- **共享**：程式碼、全域變數、heap（`malloc` 來的）、開啟的檔案
- **各自私有**：暫存器、PC、**堆疊**（區域變數）

?? 選擇 | 兩個執行緒都在同一個函式裡宣告 `int t = 0;`（區域變數）。它們的 t 是？
[ ] 同一個
[x] 各自一個
!! 區域變數放在哪裡？堆疊是共享還是私有？
>> 區域變數在堆疊上，每個執行緒有自己的堆疊。全域變數才是共享的。

為什麼用執行緒，不多開幾個行程？
- 建立、切換都**比行程便宜**（不用複製整個記憶體）
- 共享記憶體，**溝通方便**（但要小心兩個同時改同一個變數——之後的「同步」章會講）

?? 選擇 | 哪一個是執行緒「私有」的？
[ ] 全域變數
[ ] heap
[x] 堆疊
!! 每個執行緒要能各自呼叫函式。
>> 堆疊私有；全域變數和 heap 共享。

**使用者層級執行緒**：由程式庫管理，切換不用進核心，很快；但核心不知道它們，把它們當成一個。
**核心層級執行緒**：由 OS 管理，可以分到不同 CPU 平行跑。

三種對應模型（使用者執行緒 → 核心執行緒）：
- **多對一**：一個卡住（做會阻塞的系統呼叫），整個行程卡住；不能用多核心
- **一對一**（Linux、Windows）：真的平行；建立成本較高
- **多對多**：彈性大、實作複雜

?? 選擇 | 多對一模型中，一個使用者執行緒呼叫會阻塞的 `read()`，會怎樣？
[x] 整個行程的所有執行緒都卡住
[ ] 只有那個執行緒卡住
[ ] 不會阻塞
!! 核心看到的只有一個核心執行緒。
>> 唯一的核心執行緒被阻塞了，其他使用者執行緒也沒辦法跑。

?? 填空 | 一個行程有 4 個執行緒，總共有幾個堆疊？
== 4
!! 每個執行緒一個。
>> 4 個堆疊；但只有一份 heap 和全域變數。

?? 寫 | 在手寫板畫一個行程的記憶體：程式碼、全域資料、heap、兩個執行緒，標出哪些是共享、哪些是各自的。
== 共享：程式碼、全域資料、heap、開啟的檔案。
== 各自：執行緒 1 的堆疊和暫存器、執行緒 2 的堆疊和暫存器。
!! 函式呼叫用到的東西是私有的。
>> 考試最常考：heap 共享、堆疊私有。

@例題 下面兩個執行緒同時跑 `count = count + 1;` 各 1000 次（`count` 是全域變數，一開始是 0）。結束後 count 一定是 2000 嗎？
@寫 count 是共享還是私有？ | 全域變數，兩個執行緒共享同一個 count。
@寫 `count = count + 1` 其實分幾步？ | 三步：讀 count 到暫存器、加 1、寫回去。
@步 兩個交錯會怎樣 | A 讀到 5、B 也讀到 5，A 寫回 6、B 也寫回 6——加了兩次只多 1。
@答 不一定，可能小於 2000。這叫競爭條件，「同步」那一章會學怎麼用鎖解決。

=== os-process#4
title: 雙模式與系統呼叫
mins: 30
goal: 分得清使用者模式和核心模式；知道哪些是特權指令；分得清中斷和 trap；認得幾種核心架構
---
> [!先記住]
> CPU 有兩種模式：**使用者模式**只能做一般的事；**核心模式**能做所有事（碰硬體、改頁表、關中斷）。程式要請作業系統幫忙，就用**系統呼叫**：觸發一個 trap，切到核心模式，做完再切回來。

```fig
flow: 程式呼叫 read() -> trap：切到核心模式 -> 作業系統做事 -> 回到使用者模式*
```

CPU 有兩種模式（硬體上有一個模式位元）：
- **使用者模式**：一般程式在這裡跑，**不能**做危險的事
- **核心模式**：OS 在這裡跑，什麼都能做

會影響整台電腦的指令叫**特權指令**，只能在核心模式做：設定計時器、關閉中斷、直接操作 I/O、修改記憶體保護設定。

?? 選擇 | 哪一個應該是特權指令？
[ ] 兩個暫存器相加
[ ] 讀取目前時間
[x] 關閉中斷
!! 如果一般程式能做，會不會害到別人？
>> 一般程式關掉中斷，OS 就拿不回 CPU。讀時間、做加法不影響別人。

一般程式需要 OS 服務（讀檔、開網路連線）時，用**系統呼叫**：執行一個特殊的 **trap** 指令，CPU 切到核心模式、跳到 OS 預先設好的地方；OS 做完再切回使用者模式。

?? 排序 | 系統呼叫 `read()` 的過程
- 程式呼叫 `read()`，執行 trap 指令
- CPU 切到核心模式，跳到 OS 的處理程式
- OS 檢查參數、完成讀檔
- 切回使用者模式，回到程式
>> trap 是唯一合法進入核心的方式，OS 會先檢查程式要求的事合不合法。

兩種「打斷」：
- **中斷**（interrupt）：**硬體**發出、**非同步**（隨時可能來），像鍵盤按下、磁碟讀完、計時器到期
- **trap／例外**：**軟體**造成、**同步**（某個指令執行時發生），像系統呼叫、除以零

**計時器**很重要：每隔一段時間一定會產生中斷，保證 OS 一定拿得回 CPU，不會被無窮迴圈的程式霸佔。

?? 選擇 | 程式裡發生「除以零」，屬於？
[ ] 硬體中斷
[x] trap（例外）
!! 是不是某個指令執行時當場發生的？
>> 是正在執行的指令造成的，同步，屬於 trap／例外。

核心的架構：
- **單體式**：所有功能在核心裡，快，但難維護
- **微核心**：核心只留最少（通訊、排程），其他服務放到使用者空間，靠訊息溝通；穩定但多了溝通成本
- **可載入模組**（Linux）：核心可以在執行中載入新功能

?? 寫 | 在手寫板寫出：為什麼一般程式不能直接讀寫磁碟，一定要透過系統呼叫？
== 如果每個程式都能直接操作磁碟，就能讀寫別人的檔案、弄壞檔案系統。透過系統呼叫，OS 可以先檢查權限和參數，保護整台電腦。
!! 想想有很多程式、很多使用者同時在用電腦。
>> 雙模式和系統呼叫的目的就是「保護」。

@例題 判斷下列各是「中斷」還是「trap」：(1) 網路卡收到封包 (2) 程式呼叫 `fork()` (3) 存取不合法的記憶體位址 (4) 計時器到期。
@寫 (1) 和 (4) | 都是外部硬體發出、跟正在跑的指令無關：中斷。
@寫 (2) 和 (3) | 都是正在跑的指令造成的：trap（系統呼叫、例外）。
@步 判斷口訣 | 「誰造成的、什麼時候來」：硬體、隨時 → 中斷；指令當場 → trap。
@答 (1)(4) 中斷；(2)(3) trap。

=== os-process#5
title: 行程間通訊：共享記憶體與訊息傳遞
mins: 30
goal: 比較共享記憶體和訊息傳遞；知道阻塞／非阻塞；分得清一般 pipe 和 named pipe
---
> [!先記住]
> 行程彼此獨立，要交換資料有兩種方式：**共享記憶體**（開一塊大家都能讀寫的區域，快，但要自己處理同步）和**訊息傳遞**（透過作業系統送訊息，慢一點，但比較安全，也能跨機器）。

```fig
array
row 緩衝區: _ A B C _ _
idx: 0 1 2 3 4 5
cap: out = 1（下一個要拿的），in = 4（下一個要放的）。in == out 是空；(in + 1) % n == out 是滿
```

行程的記憶體是分開的，彼此看不到。要合作就需要**行程間通訊**（IPC），兩大類：

- **共享記憶體**：請 OS 開一塊兩個行程都能讀寫的記憶體。建好之後讀寫**不用經過 OS**，很快；但兩邊同時寫會出問題，要自己做同步。
- **訊息傳遞**：用 `send`、`receive` 透過 OS 傳。每次都要系統呼叫，比較慢；但 OS 會幫忙處理同步，也能跨機器。

?? 選擇 | 兩個行程要交換大量影像資料（同一台電腦），比較快的是？
[x] 共享記憶體
[ ] 訊息傳遞
!! 哪一種每次傳資料都要經過 OS？
>> 共享記憶體建好之後直接讀寫，不經過核心，適合大量資料。

**阻塞**（同步）和**非阻塞**（非同步）：
- 阻塞 send：等對方收到才繼續；阻塞 receive：等到有訊息才繼續
- 非阻塞：馬上返回，不等

兩邊都阻塞的叫 **rendezvous**（約好碰面）。

?? 選擇 | receive 是阻塞的，但目前沒有任何訊息。會怎樣？
[x] 行程停下來等，直到有訊息
[ ] 馬上回傳「沒有訊息」
[ ] 程式出錯

>> 行程進入 waiting，有訊息來才回到 ready。非阻塞版本才會馬上返回。

**Pipe**（管道）：一端寫、一端讀，像水管。
- **一般 pipe**：**單向**，只能在有親屬關係的行程之間（例如父子：fork 前建好，fork 後兩邊都有）
- **named pipe**（FIFO）：有名字，不相關的行程也能用

Shell 的 `ls | sort` 就是用 pipe 把 ls 的輸出接到 sort 的輸入。

== 2
!! 一般 pipe 是單向的。
>> 一條父→子、一條子→父。

=== os-sched#1
title: 排程的衡量標準：周轉、等待、回應時間
mins: 25
goal: 會算周轉時間、等待時間、回應時間；分得清它們的定義
---
> [!先記住]
> 排程就是決定「下一個讓誰用 CPU」。最常算的是**等待時間**：在就緒佇列裡乾等的總時間。**周轉時間**＝完成－抵達；**等待時間**＝周轉－真正執行的時間。

```fig
timeline FCFS: P1 5 | P2 3
cap: P1：周轉 5、等待 0。P2：5 才開始，8 完成，周轉 8 − 1 = 7，等待 7 − 3 = 4
```

有很多行程在 ready 佇列裡，**CPU 排程**決定下一個給誰。好不好怎麼量？

- **CPU 使用率**：CPU 忙碌的比例，越高越好
- **throughput**（產出量）：單位時間完成幾個行程
- **周轉時間** = 完成時間 − 到達時間（從來到走，全部算）
- **等待時間** = 在 ready 佇列裡等的總時間 = 周轉時間 − 執行時間
- **回應時間** = 第一次拿到 CPU 的時間 − 到達時間

?? 填空 | 行程第 2 毫秒到、要跑 5 毫秒、第 12 毫秒完成。周轉時間是幾毫秒？
== 10
!! 完成 − 到達。
>> $12-2=10$。

?? 填空 | 同一個行程，等待時間是幾毫秒？
== 5
!! 周轉時間裡，扣掉真的在跑的時間。
>> $10-5=5$。

回應時間只看「第一次」拿到 CPU。互動式程式（打字、點按鈕）最在意它——使用者希望馬上有反應，就算整件事要很久。

?? 選擇 | 一個行程第 0 毫秒到，第 3 毫秒第一次拿到 CPU，中途被換下好幾次，第 20 毫秒完成。回應時間是？
[x] 3 毫秒
[ ] 20 毫秒
[ ] 17 毫秒
!! 只看第一次拿到 CPU。
>> $3-0=3$。

注意：這裡的等待時間**只算在 ready 佇列裡等**，在等 I/O（waiting 狀態）的時間不算。

?? 排序 | 依「從到達開始算，量的範圍」從小到大
- 回應時間（到第一次拿到 CPU）
- 周轉時間（到完成）
>> 回應時間 ≤ 周轉時間。

?? 寫 | 在手寫板算：三個行程同時在 0 到，依序跑 A（6 毫秒）、B（2）、C（3）。各自的等待時間和平均。
== A 等 0、B 等 6、C 等 8，平均 $14/3\approx4.67$。
!! 每個行程等到前面的都跑完。
>> 如果先跑短的（B、C、A）：0、2、5，平均 2.33——短的先跑，大家等得少。

@例題 P1（到達 0、執行 4）、P2（到達 1、執行 3）、P3（到達 2、執行 1），依照到達順序跑完才換。算每個的周轉時間、等待時間。
@寫 寫出時間軸 | P1：0–4；P2：4–7；P3：7–8。
@寫 周轉時間＝完成 − 到達 | P1：4；P2：$7-1=6$；P3：$8-2=6$。
@步 等待時間＝周轉 − 執行 | P1：0；P2：3；P3：5。平均 $8/3\approx2.67$。
@答 周轉 4、6、6；等待 0、3、5。

=== os-sched#2
title: 排程演算法：FCFS、SJF、SRTF、優先權、RR
mins: 40
goal: 會手動畫 FCFS、SJF、SRTF、RR 的時間軸並算平均等待；知道各自的優缺點（convoy、飢餓、aging）
---
> [!先記住]
> **FCFS** 先來先做，簡單但會有**護航效應**（一個大的擋住一堆小的）。**SJF** 挑執行時間最短的先做，平均等待時間最短。可以搶占的版本叫 **SRTF**：新來的比目前的**剩餘時間**還短，就搶過來。

```fig
timeline FCFS: P1 6 | P2 8 | P3 7 | P4 3
timeline SJF: P4* 3 | P1 6 | P3 7 | P2 8
cap: FCFS 平均等待 (0 + 6 + 14 + 21) / 4 = 10.25；SJF 平均等待 (3 + 16 + 9 + 0) / 4 = 7
```

```fig
timeline RR q=2: P1 2 | P2 2 | P3 1 | P1 2 | P2 1 | P1 1
cap: P1 在 9 完成，等待 9 − 5 = 4；P2 在 8 完成，等待 5；P3 在 5 完成，等待 4。平均 13 / 3 ≈ 4.33
```

**FCFS**（先來先服務）：照到達順序，跑完才換。簡單，但短工作卡在長工作後面（**convoy effect**）。

**SJF**（最短工作優先，不搶先）：CPU 空了，選**執行時間最短**的。所有人同時到時，平均等待時間最小。

先看影片的前半：影印店的例子，和四個程式的問題。

@影片 os-srtf 0-88.7

?? 選擇 | 同時到達：A 要 8、B 要 1。哪一個順序平均等待時間比較少？
[ ] A 先
[x] B 先
!! 影片裡的影印店。
>> B 先：A 等 1、B 等 0，平均 0.5；A 先：B 等 8，平均 4。短的先做。

**SRTF**（剩餘時間最短優先）：SJF 的**可搶先**版本。有新行程到的時候，比較**大家還剩多少**，剩最少的跑（正在跑的可能被搶走）。

@影片 os-srtf 90-162.8

?? 選擇 | 第 1 毫秒時，P1 已經跑了 1 毫秒（原本要 8），P2 剛到要 4。SRTF 會？
[x] 換 P2 跑，因為 4 比 P1 剩下的 7 少
[ ] 繼續跑 P1，因為 P1 先到
[ ] 換 P2，因為 4 比 8 少
!! 比的是「還剩多少」。
>> P1 剩 7、P2 要 4，換 P2。比的是「剩下」的時間，不是原本的 8。

@影片 os-srtf 164.2-249

**優先權排程**：選優先權最高的；低優先權的可能永遠等不到（**飢餓**）。解法：**aging**——等越久，優先權慢慢提高。

**Round Robin（RR）**：每人輪流跑一個**時間片** $q$，時間到還沒跑完就排到隊尾。回應時間好，**不會飢餓**。
- $q$ 很大 → 變成 FCFS
- $q$ 太小 → 一直在 context switch，浪費

?? 填空 | RR，$q=2$。A（4）、B（3）同時在 0 到，A 先。B 什麼時候完成？
== 7
!! A 0–2、B 2–4、A 4–6（A 完成）、B 6–?
>> B 還剩 1，6–7 完成。

?? 寫 | 在手寫板畫 SJF（不搶先）的時間軸：P1（到 0、執行 7）、P2（到 2、執行 4）、P3（到 4、執行 1），並算平均等待。
== P1 0–7（只有它）；7 時 P2、P3 都在，選短的 P3：7–8；P2：8–12。
== 等待：P1 0、P3 $8-4-1=3$、P2 $12-2-4=6$，平均 3。
!! 不搶先：P1 先跑完。之後選最短的。
>> SRTF 會在 2 時就讓 P2 先跑，平均等待會更少。

@例題 P1（到 0、執行 5）、P2（到 1、執行 3）、P3（到 2、執行 1）。用 SRTF 畫時間軸，算平均等待時間。

=== os-sched#3
title: 即時排程：Rate-monotonic 與 EDF
mins: 35
goal: 會算使用率 $U$；會用 RM 的充分條件和 EDF 的 $U\le1$ 判斷可不可以排；會畫時間軸驗證
---
> [!先記住]
> RMS：週期短的優先權固定比較高，總使用率 $\le n(2^{1/n}-1)$ 保證排得完；EDF：截止期限近的先做，總使用率 $\le1$ 就行。

```fig
timeline RMS: P1* 20 | P2 30 | P1* 20 | P2 5 | · 25
cap: P1 週期 50、執行 20；P2 週期 100、執行 35。週期短的 P1 優先權高，一到就搶；P2 在 75 做完，趕上 100 的期限
```

**即時系統**：工作有**截止時間**，錯過就失敗（例如煞車控制）。常見模型：週期性工作 $i$，每 $p_i$ 時間來一次、每次要跑 $t_i$，截止時間是下一次來之前。

**使用率** $U=\sum\frac{t_i}{p_i}$。一定要 $U\le1$，否則 CPU 根本不夠用。

?? 填空 | 工作 A：週期 20、執行 5；工作 B：週期 50、執行 10。使用率 $U$ 是多少？
== 0.45
!! $\frac5{20}+\frac{10}{50}$。
>> $0.25+0.2=0.45$。

**Rate-monotonic（RM）**：**週期越短，優先權越高**（固定不變），可搶先。

RM 的**充分條件**：$U\le n(2^{1/n}-1)$。
- $n=1$：1
- $n=2$：約 0.828
- $n\to\infty$：約 0.693（$\ln2$）

滿足就**一定**排得出來；不滿足**不一定**失敗，要畫時間軸驗證。

?? 選擇 | 兩個工作，$U=0.75$。用 RM 一定排得出來嗎？
[x] 一定可以
[ ] 一定不行
[ ] 要畫時間軸才知道
!! $n=2$ 的界線是 0.828。
>> $0.75\le0.828$，滿足充分條件，一定可以。

**EDF**（最早截止優先）：**截止時間越早，優先權越高**（動態改變），可搶先。條件很簡單：$U\le1$ **就一定**排得出來（充要條件）。

?? 選擇 | 兩個工作 $U=0.9375$。RM 和 EDF 的結論是？
[x] EDF 一定可以；RM 不確定，要畫時間軸
[ ] 兩個都一定可以
[ ] 兩個都一定不行
!! RM 界線 0.828、EDF 界線 1。
>> 超過 0.828 不代表 RM 一定失敗，要驗證；EDF 只要 $\le1$ 就可以。

?? 寫 | 在手寫板畫 RM 的時間軸：$P_1$（$p=50,t=25$）、$P_2$（$p=80,t=35$），看 $P_2$ 有沒有在 80 前完成。
== 0–25 跑 $P_1$；25–50 跑 $P_2$（剩 10）；50 $P_1$ 第二次來，週期短優先權高，搶走：50–75 跑 $P_1$；75–85 跑 $P_2$。
== $P_2$ 在 85 才完成，錯過 80 的截止——RM 失敗。
!! 每到 50 的倍數，$P_1$ 都會來搶。
>> 同一組用 EDF：50 時 $P_2$ 截止 80 比 $P_1$ 的 100 早，$P_2$ 繼續跑到 60 完成，成功。

@例題 $P_1$（$p=4,t=1$）、$P_2$（$p=6,t=2$）、$P_3$（$p=12,t=3$）。算 $U$，判斷 RM 和 EDF 能不能排。
@寫 算 $U$ | $\frac14+\frac26+\frac3{12}=0.25+0.333+0.25\approx0.833$。
@寫 RM 的充分條件（$n=3$） | $3(2^{1/3}-1)\approx0.780$。$0.833>0.780$，充分條件不成立，要畫時間軸。
@步 EDF | $U\le1$，一定可以。（RM 畫出 0–12 的時間軸也排得出來：條件只是充分，不是必要。）
@答 $U\approx0.833$；EDF 一定可以；RM 不滿足充分條件，但實際畫時間軸可行。

=== os-sched#4
title: 多處理器排程與實務：親和性、負載平衡、Linux CFS
mins: 25
goal: 知道處理器親和性和負載平衡互相拉扯；知道 MLFQ 怎麼升降級；知道 Linux CFS 用 vruntime 和紅黑樹
---
> [!先記住]
> 多處理器排程：要平衡每顆 CPU 的工作（負載平衡），又要盡量讓行程留在同一顆 CPU（親和性），cache 才不用重新暖。

```fig
flow: CPU 0：佇列很長! -> 推一個給別人（push）
flow: CPU 1：閒著 -> 自己拉一個來（pull）*
cap: 負載平衡的兩種做法；但搬走的行程，cache 要重新暖起來
```

**多層佇列**（MLQ）：依類別分成好幾個佇列（例如互動式、批次），佇列之間有固定優先權。行程不能換佇列。

**多層回饋佇列**（MLFQ）：可以換。
- 用完時間片還沒跑完 → **降級**（可能是長工作）
- 等太久 → **升級**（防止飢餓）

結果：短的、互動式的留在高優先權；長的慢慢沉到底下。

?? 選擇 | MLFQ 中，一個行程每次都用完整個時間片，它會？
[x] 慢慢被降到低優先權的佇列
[ ] 一直留在最高優先權
[ ] 被終止
!! 用完時間片代表它可能是什麼樣的工作？
>> 很可能是計算很久的工作，降級讓短工作先跑。

多顆 CPU 時：
- **處理器親和性**（affinity）：行程盡量留在同一顆 CPU 上，因為那顆的**快取**裡還有它的資料。
- **負載平衡**：把行程從忙的 CPU 搬到閒的（push／pull）。

這兩個**互相拉扯**：搬過去平衡了負載，卻丟掉了快取。

?? 選擇 | 為什麼要有處理器親和性？
[x] 留在同一顆 CPU，快取裡的資料還能用
[ ] 讓每顆 CPU 一樣忙
[ ] 讓行程不會飢餓
!! 換到別的 CPU，快取裡有它的資料嗎？
>> 新的 CPU 快取是空的，要重新從記憶體載入，很慢。

**Linux CFS**（完全公平排程）：每個行程記一個 **vruntime**（虛擬執行時間，依 nice 值加權）。每次挑 vruntime **最小**的跑——跑得最少的優先。用紅黑樹存，找最小、插入都是 $O(\lg n)$。

?? 填空 | CFS 用紅黑樹存 $n$ 個行程。找出 vruntime 最小的那個，最多要多少時間？（寫 lgn 或 1）
== lgn
== lg n
== 1
!! 最小的在最左邊；也可以一直記住它。
>> 走到最左邊 $O(\lg n)$；實作上會快取最左節點，取出是 $O(1)$、插入 $O(\lg n)$。

**Little 公式**：佇列平均長度 $n=\lambda W$（到達率 × 平均等待時間）。每秒來 7 個、平均等 2 秒 → 佇列平均 14 個。

?? 寫 | 在手寫板寫出：親和性和負載平衡各自的好處，以及為什麼會衝突。
== 親和性：保住快取，少花時間重新載入。負載平衡：每顆 CPU 都有事做，不會有的忙死、有的閒著。
== 衝突：為了平衡把行程搬走，就失去原本 CPU 快取裡的資料。
!! 一個想「留下」，一個想「搬走」。
>> 實際系統會設門檻：負載差太多才搬。

@例題 一個排隊系統每秒平均來 5 個請求，佇列裡平均有 20 個請求在等。每個請求平均等多久？
@寫 寫出 Little 公式 | $n=\lambda W$
@寫 代入、解 $W$ | $20=5\times W$，$W=4$ 秒。
@步 解讀 | 想讓大家等少一點，要嘛處理得更快（佇列變短），要嘛限制到達率。
@答 平均等 4 秒。

=== os-sync#1
title: 競爭條件與臨界區的三個條件
mins: 35
goal: 會解釋 count++ 為什麼會出錯（競爭條件）；說得出臨界區要滿足的互斥、progress、bounded waiting；會判斷兩個常見的錯誤解法違反哪一條
---
> [!先記住]
> 兩個執行緒同時改同一個變數，結果看誰先誰後而不同，叫**競爭條件**。改共享資料的那段程式叫**臨界區**。好的解法要同時滿足：**互斥、進展、有限等待**。

```fig
array
row A：讀 count: 5
row B：讀 count: 5
row A：寫回 6: 6
row B：寫回 6: 6!
cap: 兩個人都加 1，結果只加了 1。這就是競爭條件
```

先看影片：兩個執行緒各加 1，結果竟然只加了 1。

@影片 os-sync 0-66.1

`count++` 在機器裡其實是三步：**讀**到暫存器、**加 1**、**寫回**。兩個執行緒交錯執行，就可能互相蓋掉。

結果取決於執行順序，這叫**競爭條件**（race condition）。

?? 選擇 | `count` 一開始是 0，兩個執行緒各做一次 `count++`（沒有任何保護）。最後 `count` 可能是？
[ ] 只可能是 2

=== os-sync#2
title: Peterson 演算法：兩個行程的正確解法
mins: 30
goal: 會寫 Peterson 的進入區；能說明它為什麼滿足互斥與 bounded waiting；知道它只限兩個行程、而且怕指令被重排
---
> [!先記住]
> 只用一個 `turn` 輪流：互斥對，但**違反進展**（輪到你但你不想進，我也進不去）。只用 `flag` 表示想進：兩人同時舉手會**互相等到死**。**Peterson** 把兩個結合：先舉手，再把順序**讓給對方**。

```fig
flow: 我舉手 flag[i] -> 讓給對方 turn = j
flow: 對方想進又輪到他？ -> 是：等 | 否：進去*
```

把兩個錯誤解法合起來：**舉旗**表示我想進，**turn** 表示禮讓。

```c
// 行程 P_i，對方是 j = 1 - i
flag[i] = true;                 // 我想進
turn = j;                       // 但你先
while (flag[j] && turn == j) ;  // 你想進、而且輪到你，我就等
/* 臨界區 */
flag[i] = false;                // 我用完了
```

?? 選擇 | $P_0$ 執行 `turn = 1` 是什麼意思？
[x] 如果兩個都想進，讓 $P_1$ 先
[ ] $P_0$ 放棄進入
[ ] $P_1$ 一定會先進入
!! 只有雙方都舉旗時 turn 才有作用。
>> 是禮讓。如果 $P_1$ 根本沒舉旗，$P_0$ 還是直接進。

?? 排序 | 依序排出 Peterson 進入區的三行
- `flag[i] = true;`
- `turn = j;`
- `while (flag[j] && turn == j) ;`
>> 先表態、再禮讓、再等。

**為什麼互斥？** 假設兩人同時在臨界區，那 flag[0]、flag[1] 都是 true。turn 只有一個值，**最後寫 turn 的那個人**寫的是「對方」，它會看到 `flag[對方] && turn==對方` 成立而卡住——矛盾。

**為什麼 bounded waiting？** $P_i$ 在等的時候，$P_j$ 用完出來想再進，會先寫 `turn = i`，自己被擋住。所以 $P_i$ 最多等 $P_j$ 一次。

?? 選擇 | $P_0$ 在 while 迴圈等待。$P_1$ 最多還能先進入臨界區幾次？
[x] 1 次
[ ] 2 次
[ ] 沒有上限
!! $P_1$ 想再進一次時，會先寫 turn 給誰？
>> 再進之前寫了 `turn = 0`，就輪 $P_0$ 了。

?? 寫 | 在手寫板證明 Peterson 滿足互斥（用反證）。
== 假設 $P_0$、$P_1$ 都在臨界區 ⇒ flag[0]=flag[1]=true。
== 不妨設 $P_0$ 比較晚寫 turn，寫的是 turn=1；之後 turn 沒再改。
== $P_0$ 要通過 while，需要 flag[1]=false 或 turn≠1，兩個都不成立——矛盾。
!! 關鍵是「誰最後寫 turn」。
>> 這是費曼關卡常考的推理鏈。

限制：
- **只能兩個行程**（$n$ 個行程要用 Bakery 演算法：拿號碼牌，號碼一樣比編號）
- 假設讀寫照程式順序。現代 CPU 和編譯器可能把 `flag[i]=true` 和讀 `flag[j]` **對調**，兩個都看到對方是 false 就一起進去了（下一個知識點講硬體怎麼處理）

@例題 $P_0$、$P_1$ 幾乎同時要進入。順序：$P_0$ 寫 flag[0]=true；$P_1$ 寫 flag[1]=true；$P_0$ 寫 turn=1；$P_1$ 寫 turn=0。誰先進去？
@寫 最後的 turn 是多少 | 最後 $P_1$ 寫了 turn=0。
@寫 檢查兩人的 while | $P_0$：flag[1]=true 但 turn≠1 → 通過；$P_1$：flag[0]=true 且 turn==0 → 等。
@步 結論 | 最後寫 turn 的人（$P_1$）禮讓成功，$P_0$ 先進。
@答 $P_0$ 先進入。

=== os-sync#3
title: 硬體支援：test_and_set、compare_and_swap
mins: 30
goal: 知道原子指令的意思；會用 test_and_set 寫一把鎖；會判斷 compare_and_swap 的結果；知道關中斷只在單處理器可行
---
> [!先記住]
> 硬體提供原子指令（讀和寫一次完成、不會被打斷），test_and_set 或 compare_and_swap 一行就能做出一把鎖。

```fig
flow: test_and_set(&lock) -> 回傳 false：原本沒鎖，搶到了* | 回傳 true：別人拿著，繼續轉!
```

軟體解法又慢又怕重排。CPU 直接提供**原子**（atomic）指令：一條指令做完「讀＋改」，中間**不可能被插隊**。

**`test_and_set(&lock)`**：回傳 lock 的**舊值**，並把 lock 設成 true。

```c
while (test_and_set(&lock)) ;   // 舊值是 true：別人拿著，繼續等
/* 臨界區 */
lock = false;
```

?? 選擇 | lock 一開始是 false。$P_0$ 執行 `test_and_set(&lock)`，回傳什麼？lock 變成什麼？
[x] 回傳 false；lock 變 true
[ ] 回傳 true；lock 變 true
[ ] 回傳 false；lock 還是 false
!! 回傳舊值，設成 true。
>> 回傳 false 所以 $P_0$ 跳出迴圈進入；之後的人都拿到 true，只能等。

這把簡單的鎖：互斥 ✓、progress ✓，但**不保證 bounded waiting**——放開鎖時誰搶到是運氣，某個人可能一直搶不到。

改良：加一個 `waiting[]` 陣列，離開時從 $i+1$ 開始**繞一圈**找下一個在等的人，直接把位子交給他。每個人最多等 $n-1$ 輪。

?? 選擇 | 只用 `while(test_and_set(&lock));` 的鎖，不滿足哪個條件？
[ ] 互斥
[x] Bounded waiting
[ ] Progress
!! 放開鎖之後誰會拿到？
>> 誰搶到是隨機的，沒有上限。

**`compare_and_swap(&v, expected, new)`**：如果 $v$ 等於 expected，就把 $v$ 改成 new；不管怎樣都**回傳舊值**。常用來做原子的加 1、無鎖的資料結構。

?? 填空 | $v=5$。執行 `compare_and_swap(&v, 5, 9)` 之後，$v$ 是多少？
== 9
!! $v$ 跟 expected 一樣嗎？
>> 5 等於 5，所以改成 9；回傳舊值 5。

?? 寫 | 在手寫板用 compare_and_swap 寫一個原子的 `count++`。
== `do { old = count; } while (compare_and_swap(&count, old, old + 1) != old);`
== 意思：讀到 old；如果這段時間 count 沒被別人改，就換成 old+1；被改了就重讀重來。
!! 回傳值不是 old，代表別人插隊改過了。
>> 這就是「樂觀」的做法：先做，失敗就重試。

**關中斷**：進臨界區前把中斷關掉，就不會被切換。只在**單處理器**可行；多處理器上別顆 CPU 照跑，而且關中斷太久很危險。

**記憶體屏障**（memory barrier）：一條指令，保證它前後的讀寫不會被對調。Peterson 要在多核心上正確，就要加。

@例題 $v=3$。兩個執行緒同時做：A 執行 `compare_and_swap(&v, 3, 4)`，B 執行 `compare_and_swap(&v, 3, 7)`。可能的結果？
@寫 原子：一定一個先、一個後 | 假設 A 先：$v=3$ 等於 3，改成 4，A 拿到回傳 3。
@寫 B 接著做 | $v=4\ne3$，不改；B 拿到回傳 4，知道失敗了。
@步 反過來 | B 先：$v=7$，A 失敗。
@答 $v$ 是 4 或 7（不會是別的），而且只有一個人成功。

title: 號誌：wait 和 signal、生產者消費者
mins: 40
goal: 會寫號誌的 wait／signal；會用號誌強制先後順序；會寫有限緩衝區的生產者消費者，知道 wait 順序寫反會卡死；知道讀者寫者、哲學家問題的重點
---
> [!先記住]
> **號誌**是一個整數，只能用兩個原子操作：**wait**（減 1，不夠就去睡）和 **signal**（加 1，有人在睡就叫醒一個）。初值 1 就是互斥鎖；初值 $n$ 代表有 $n$ 份資源。

```fig
flow: wait(S)：S 減 1 -> S < 0 就去睡!
flow: signal(S)：S 加 1 -> 有人在睡就叫醒一個*
```

**號誌**（semaphore）$S$ 是一個整數，加上兩個原子操作：

```c
wait(S)   { S.value--; if (S.value < 0) { 進入 S 的等待佇列; 睡覺; } }
signal(S) { S.value++; if (S.value <= 0) { 從佇列叫醒一個; } }
```

值是負的時候，**絕對值＝在等的人數**。用佇列睡覺，不會一直空轉。

?? 填空 | 號誌 $S$ 初值 1。三個行程依序 wait(S)。$S$ 的值是多少？有幾個在等？
== $S=-2$，2 個在等。
!! 每次 wait 減 1；第一個成功，後兩個睡。
>> $1-3=-2$，絕對值 2 就是等待人數。

**用法 1：互斥**——初值 1，進去前 wait、出來 signal。

**用法 2：強制順序**——要 $P_1$ 的 S1 先於 $P_2$ 的 S2：`synch` 初值 **0**。
- $P_1$：`S1; signal(synch);`
- $P_2$：`wait(synch); S2;`

?? 選擇 | 上面的 synch 初值為什麼是 0？
[x] 讓 $P_2$ 在 $P_1$ signal 之前一定要等
[ ] 讓兩個都能馬上進
[ ] 隨便，1 也可以
!! 初值 1 的話，$P_2$ 的 wait 會怎樣？
>> 初值 0，wait 一定睡，直到 $P_1$ signal。

**有限緩衝區**（大小 $n$）：`mutex=1, empty=n, full=0`
```c
生產者: wait(empty); wait(mutex); 放入; signal(mutex); signal(full);
消費者: wait(full);  wait(mutex); 取出; signal(mutex); signal(empty);
```
empty＝空格數，full＝有東西的格數。

?? 寫 | 在手寫板說明：如果生產者寫成先 `wait(mutex)` 再 `wait(empty)`，緩衝區滿的時候會怎樣？
== 生產者拿著 mutex，睡在 empty 上（沒有空格）。
== 消費者要 wait(mutex) 才能取出，但 mutex 在生產者手上 → 兩邊永遠卡住。
!! 誰拿著 mutex 睡著了？
>> 兩個 signal 對調則沒關係（signal 不會讓人睡）。

**讀者寫者**（讀者優先）：很多讀者可以一起讀；寫者要獨占。第一個讀者進來時鎖住寫者，最後一個讀者離開才放。缺點：讀者源源不絕，寫者**飢餓**。

**哲學家用餐**：5 人圍桌、5 支筷子，每人先拿左再拿右 → 可能 5 人都拿著左筷等右筷。解法：最多 4 人上桌；兩支一起拿；奇數號先左、偶數號先右。

?? 選擇 | 讀者優先的讀者寫者解法中，誰可能飢餓？
[ ] 讀者
[x] 寫者
[ ] 都不會
!! 讀者一直來，最後一個讀者什麼時候才會離開？
>> 只要還有讀者在讀，新讀者就能進來，寫者一直等。

@例題 三個行程 A、B、C，要求 A 做完才能做 B，B 做完才能做 C。用號誌寫出來，並寫初值。
@寫 需要幾個號誌 | 兩個：$s_1$（A→B）、$s_2$（B→C），初值都是 0。
@寫 寫出每個行程 | A：`做事; signal(s1);`　B：`wait(s1); 做事; signal(s2);`　C：`wait(s2); 做事;`
@步 檢查 | C 先跑會睡在 $s_2$；B 先跑會睡在 $s_1$；只有 A 能先完成 ✓。

- **死結**（deadlock）：一群行程互相等對方手上的東西，**全部**永遠卡住。例：A 拿著鎖 1 等鎖 2，B 拿著鎖 2 等鎖 1。
- **飢餓**（starvation）：某個行程一直被別人插隊，**它**永遠等不到（其他人照樣在跑）。
- **活鎖**（livelock）：大家都在動，但一直互相讓來讓去，沒有進展（像兩個人在走廊同時往同一邊閃）。

[ ] 飢餓
[ ] 活鎖
!! 是不是所有相關的行程都卡住？
>> 兩個都永遠等，是死結。下一章會詳細學死結的條件和處理方式。

?? 選擇 | 「死結的行程一定也在飢餓」「飢餓的行程一定在死結」，哪一句對？
[x] 只有第一句對
[ ] 只有第二句對
[ ] 兩句都對
!! 飢餓的時候，別人有沒有在跑？
>> 死結的人當然等不到（飢餓）；但飢餓時其他人還在跑，不是死結。

**優先權反轉**（priority inversion）：
- 低優先權的 L 拿著一把鎖
- 高優先權的 H 要這把鎖，只好等 L
- 中優先權的 M 不需要鎖，但一直搶走 L 的 CPU
- 結果 H 被 M 間接卡住

解法 **priority inheritance**：L 拿著鎖的期間，暫時**繼承** H 的優先權，M 就搶不走。（火星探路者號真的發生過。）

?? 排序 | 優先權反轉發生的順序
- L 拿到鎖
- H 要同一把鎖，等 L
- M 一直搶占 L 的 CPU
- H 被拖住，比 M 還晚完成
>> 加上 priority inheritance，L 會用 H 的優先權跑完、放鎖。

**Spinlock**（忙等的鎖）：等的時候一直空轉。適合**多核心而且臨界區很短**（短於兩次 context switch）；單核心上空轉毫無意義（拿鎖的人根本沒在跑）。

?? 寫 | 在手寫板判斷對錯並說明理由：(1) binary semaphore 和 mutex 完全一樣 (2) Peterson 可以直接用在多核心 (3) 監視器的 signal 沒人等時會被保留
== (1) ✗：mutex 有擁有者（誰 lock 誰 unlock），號誌沒有
== (2) ✗：讀寫可能被重排，要加記憶體屏障
== (3) ✗：沒人等就什麼都沒發生
!! 三句都是考試很愛出的陷阱。
>> 另外：「所有號誌操作都會忙等」也是 ✗（用等待佇列就不會）。

@例題 高 H、中 M、低 L 三個行程。$t=0$ L 拿到鎖；$t=1$ H 到達要鎖；$t=2$ M 到達（不用鎖，要跑 5）。L 還要跑 2 才放鎖，H 拿到鎖後要跑 1。用和不用 priority inheritance，H 各在什麼時候完成？

@寫 用 priority inheritance | $t=1$ 起 L 繼承 H 的優先權，M 搶不走；L 跑完剩下的 2 到 $t=3$；H 跑到 $t=4$。
@步 比較 | 9 vs. 4：M 不再插在 H 前面。
@答 不用：$t=9$；用：$t=4$。

**死結**：一群行程，每個都在等**別人手上**的資源，誰都等不到。

=== os-deadlock#2
title: 資源配置圖與處理死結的四種方式
mins: 35
goal: 會畫資源配置圖並判斷有沒有死結；知道單一實例和多實例時「有環」的意義不同；分得清預防、避免、偵測復原、忽略；能證明資源排序可以防止死結

> **預防**：從設計上打破四個條件之一（最常用的是把資源編號、照順序申請，打破循環等待）。**避免**：每次分配前檢查會不會進入不安全狀態（Banker）。**偵測與復原**：讓它發生，再找出來處理。**忽略**：大部分作業系統的實際做法。

=== os-deadlock#3
title: Banker 演算法：先確認安全，才配置
mins: 40
goal: 會用 Max、Allocation、Need、Available 跑安全演算法找安全序列；會處理一個資源請求；知道安全、不安全、死結三者的關係；會算「至少要幾個資源才不會死結」
---
> [!先記住]
> **Banker**：每個行程事先宣告最多要多少（Max）。有人申請時，**假裝給他**，再跑一次**安全檢查**：找得到一個讓大家都能做完的順序才真的給，找不到就讓他等。

```fig
flow: Work = 3 -> P1 需 2：做完，Work = 5
flow: P0 需 5：做完，Work = 10 -> P2 需 7：做完*
cap: 安全順序 ⟨P1, P0, P2⟩
```

**避免**死結：每次要配置之前先想：配了之後，還能不能讓**所有人都做完**？

資料（$n$ 個行程、$m$ 類資源）：
- `Available`：現在剩多少
- `Max[i]`：$P_i$ 最多會要多少
- `Allocation[i]`：$P_i$ 手上已經有多少
- `Need[i] = Max[i] − Allocation[i]`：還要多少

?? 填空 | $P_1$ 的 Max 是 7、Allocation 是 3。Need 是多少？
== 4
!! Max 減 Allocation。
>> 它最多還會再要 4 個。

**安全狀態**：存在一個順序（**安全序列**），照順序每個行程都能拿到它的 Need、做完、把手上的全部還回來。

**安全演算法**：
1. `Work = Available`
2. 找一個還沒做完、而且 `Need[i] ≤ Work` 的 $P_i$
3. 讓它做完：`Work += Allocation[i]`，回到 2
4. 全部都做完 ⇒ 安全

時間 $O(mn^2)$。

?? 寫 | 在手寫板跑安全演算法：一類資源共 12 個，Available＝3。P0：Max 10、Alloc 5；P1：Max 4、Alloc 2；P2：Max 9、Alloc 2。安全嗎？
== Need：P0＝5、P1＝2、P2＝7。Work＝3：只有 P1（2 ≤ 3）能做 → Work＝3+2＝5
== P0（5 ≤ 5）→ Work＝10；P2（7 ≤ 10）→ Work＝12。安全序列 ⟨P1, P0, P2⟩
!! 先算 Need，再找 Need ≤ Work 的。
>> 安全。

**請求**：$P_i$ 要 Request：
1. Request > Need：錯誤（超過它說的最大值）
2. Request > Available：先等
3. **假裝配給它**，跑安全演算法；安全才真的配，不安全就讓它等

安全、不安全、死結的關係：
- 安全 ⇒ 一定不會死結
- **不安全不一定死結**（行程不一定真的會要到 Max），只是 OS 不能保證
- 死結 ⊂ 不安全

?? 選擇 | 「系統進入不安全狀態就一定會死結」對嗎？
[ ] 對
[x] 不對
!! 不安全是「沒辦法保證」，還是「一定出事」？
>> 行程可能沒有真的要到最大需求。

**至少要幾個資源**：$n$ 個行程，每個最多要 $k$ 個同類資源。最壞情況是每個人都拿到 $k-1$ 個、都在等最後一個；再多 1 個就有人能做完：
$$m\ge n(k-1)+1$$

?? 填空 | 3 個行程，每個最多同時需要 4 個同類資源。系統至少要幾個資源，才保證不會死結？
== 10
!! $n(k-1)+1$。
>> $3\times3+1=10$。

@例題 接著上面的例子（Available＝3，Need：P0＝5、P1＝2、P2＝7）。現在 P2 要 1 個資源，可以給嗎？
@寫 檢查 | Request＝1 ≤ Need＝7 ✓；1 ≤ Available＝3 ✓
@寫 假裝配置後 | Available＝2，P2 的 Alloc＝3、Need＝6。跑安全：只有 P1（2 ≤ 2）→ Work＝4；P0 要 5 > 4、P2 要 6 > 4，卡住。
@步 結論 | 不安全 → 不能給，P2 要等。
@答 不能給（給了會進入不安全狀態）。

=== os-deadlock#4
title: 死結復原：終止行程或搶占資源
mins: 25
goal: 知道偵測到死結之後的兩種復原方式；知道「一次終止一個」的代價；知道搶占要處理的三件事（選誰、rollback、飢餓）；會選擇犧牲者
---
> [!先記住]
> 允許死結發生，定期**偵測**：資源都只有一個時，看**等待圖**有沒有環；有多個時，用類似 Banker 的演算法（但用**目前的申請量**，不是最大需求）。找到了就**復原**：殺掉行程或搶走資源。

```fig
graph
nodes: P1@0,0 P2@1,0 P3@1,1 P4@0,1
edges: P1>P2! P2>P3! P3>P1! P4>P1
cap: 等待圖（P → P 表示在等對方）：P1、P2、P3 成環，死結；P4 只是在等，不在環上
```

偵測到死結之後，要把它解開。兩種方法：

**1. 終止行程**
- 全部終止：簡單、一定解開，但做了很久的工作全部白費
- **一次終止一個**，直到死結解開：損失比較小，但**每終止一個都要重新偵測**一次

?? 選擇 | 「一次終止一個行程直到死結解除」的主要代價是？
[x] 每終止一個都要重新跑一次偵測
[ ] 所有工作都白費
[ ] 可能造成新的死結
!! 怎麼知道死結解開了沒？
>> 要再偵測。全部終止就不用，但損失大。

選誰先終止？看：優先權、已經跑了多久、還要多久、手上有多少資源、是互動式還是批次……

**2. 搶占資源**：把資源從某個行程手上拿走，給別人。要處理三件事：
1. **選犧牲者**：搶誰的成本最小
2. **Rollback**：被搶的行程要退回到某個安全的狀態重來（最簡單是整個重跑）
3. **飢餓**：不能每次都選同一個行程當犧牲者（成本裡要算「被搶過幾次」）

?? 排序 | 用搶占資源復原時，要處理的事依序是？
- 選一個犧牲者（成本最小）
- 把它 rollback 到安全的狀態
- 記錄它被搶過的次數，避免一直選到它
>> 第三步防止飢餓。

?? 選擇 | 每次都挑「成本最小」的行程當犧牲者，可能造成什麼問題？
[x] 同一個行程一直被選中，永遠做不完（飢餓）
[ ] 死結
[ ] 沒有問題
!! 成本最小的會不會每次都是同一個？
>> 所以成本要加上「已經被選過幾次」。

?? 寫 | 在手寫板寫出：偵測多久做一次？做得很頻繁、和做得很少，各有什麼優缺點？
== 很頻繁：死結一發生就發現，卡住的行程少；但偵測本身很花 CPU。
== 很少（例如 CPU 使用率掉下來才做）：成本低；但死結可能已經拖住很多行程，也很難知道是誰「造成」的。

>> 實務上大多數一般作業系統乾脆忽略死結。

=== os-memory#1
title: 位址繫結：程式裡的位址不是真的位址
mins: 25
goal: 分得清邏輯位址和實體位址；知道三種位址繫結的時機；會用 base（重定位）暫存器和 limit 暫存器做轉換和保護
---
```fig
flow: CPU 給的邏輯位址 346 -> ＋ 重定位暫存器 14000 -> 實體位址 14346*
cap: 再加一個界限暫存器：邏輯位址超過界限就 trap，保護其他程式
```

程式裡寫的位址（變數、函數在哪）跟它**實際**在記憶體的位置，不一定一樣。

- **邏輯位址**（虛擬位址）：CPU／程式看到的
- **實體位址**：記憶體真正的位置

什麼時候決定「程式放在記憶體哪裡」（**位址繫結**）：
1. **編譯時期**：先知道會放哪，直接寫死（不能搬）
2. **載入時期**：載入時才決定（載入後不能搬）
3. **執行時期**：每次存取才轉換 → 需要硬體 **MMU**，行程可以在執行中被搬到別的地方

?? 選擇 | 行程在執行的中途被搬到記憶體的另一個位置，還能繼續跑。這需要哪一種位址繫結？
[ ] 編譯時期
[ ] 載入時期
[x] 執行時期
!! 誰在每次存取時做轉換？
>> 執行時期繫結，用 MMU 轉換。只有它的邏輯位址 ≠ 實體位址。

最簡單的 MMU：兩個暫存器
- **base**（重定位暫存器）：實體位址＝base＋邏輯位址
- **limit**：邏輯位址必須 < limit，否則 **trap**（越界存取）

?? 填空 | base＝14000，邏輯位址 346。實體位址是多少？
== 14346
!! 直接相加。
>> 程式完全不知道自己在 14000。

?? 寫 | 在手寫板：base＝3000、limit＝1200。邏輯位址 0、1199、1200 各會怎樣？
== 0 → 3000；1199 → 4199
== 1200 不小於 limit → trap（越界）
!! 先檢查 < limit，再加 base。
>> 這樣行程就不能碰到別人的記憶體。

?? 選擇 | 用 base＋limit 暫存器時，為什麼使用者程式不能自己改這兩個暫存器？
[x] 改了就能存取別人的記憶體；只有核心模式能改
[ ] 改了會變慢
[ ] 其實可以隨便改
!! 這兩個暫存器在保護什麼？
>> 載入它們是特權指令，context switch 時由 OS 設定。

@例題 兩個行程：A 的 base 5000、limit 2000；B 的 base 7000、limit 3000。A 存取邏輯位址 2500、B 存取邏輯位址 2500，各發生什麼？

@寫 B | 2500 < 3000 → 實體 9500 ✓
@步 結論 | limit 擋住 A 偷看 B
@答 A 被 trap；B 存取實體位址 9500。

=== os-memory#2
title: 連續配置：first-fit、best-fit、worst-fit 與外部碎片
mins: 30
goal: 會用三種策略把行程放進記憶體的空洞；知道外部碎片是什麼、50% 規則；知道 compaction 的條件
---
> [!先記住]
> 每個行程拿一整塊連續的記憶體。空閒的洞要選哪個：**first fit**（第一個夠大的）、**best fit**（夠大裡最小的）、**worst fit**（最大的）。用久了洞會變得很碎，總量夠卻放不下，叫**外部碎裂**。

```fig
array
row 記憶體: OS P1 _ P2 _ _ P3 _
cap: 空格是洞。三個洞加起來有 4 格，但最大的連續洞只有 2 格：想放 3 格的行程放不下，這就是外部碎裂
```

**連續配置**：每個行程放在記憶體裡**連續**的一段。記憶體裡有很多大小不一的**空洞**，新行程要選一個放：
- **First-fit**：第一個夠大的
- **Best-fit**：夠大的裡面**最小**的（要找遍）
- **Worst-fit**：**最大**的那個

?? 選擇 | 空洞依序是 100、500、200、300、600（KB）。要放 212 KB，first-fit 會選哪一個？
[x] 500
[ ] 300
[ ] 600
!! 從頭找第一個 ≥ 212 的。
>> best-fit 選 300、worst-fit 選 600。

?? 寫 | 在手寫板：同樣的空洞（100、500、200、300、600），依序放 212、417、112、426。用 best-fit，每個放哪裡？全部放得下嗎？
== 212 → 300（剩 88）；417 → 500（剩 83）
== 112 → 200（剩 88）；426 → 600（剩 174）。全部放得下
!! 每次都挑「放得下的最小洞」。
>> 這一題 first-fit 和 worst-fit 都放不下 426。

**外部碎片**：空洞**加起來**夠大，但每一個都太小、不連續，放不下。

**50% 規則**：用 first-fit，配置了 $N$ 塊，大約另外有 $0.5N$ 塊因為碎片浪費掉——約 **1/3** 的記憶體不能用。

?? 填空 | 50% 規則：配置 $N$ 塊、浪費 $0.5N$ 塊。浪費的佔全部的幾分之幾？（寫成 a/b）
== 1/3
!! $\frac{0.5N}{N+0.5N}$。
>> 三分之一。

解法：
- **Compaction**（緊縮）：把行程搬到一起，空洞合併。要**執行時期繫結**才能搬，而且很花時間
- 不要求連續：分頁、分段（後面兩節）

?? 選擇 | 下面哪一個策略通常**最差**？
[ ] First-fit
[ ] Best-fit
[x] Worst-fit
!! 每次都切最大的洞，大洞會怎樣？
>> 大洞被切碎，之後大的行程放不下。first-fit 快，利用率和 best-fit 差不多。

@例題 同樣的空洞（100、500、200、300、600）、同樣的請求（212、417、112、426），用 first-fit。哪一個放不下？
@寫 前兩個 | 212 → 500（剩 288）；417 → 600（剩 183）
@寫 後兩個 | 112 → 288 那個洞（剩 176）；426：剩下 100、176、200、300、183，都不夠
@步 觀察 | 空洞總和 959 KB > 426，但沒有一個連續夠大——外部碎片
@答 426 放不下（要等）。

=== os-memory#3
title: 分頁：位址拆成頁號和位移
mins: 40
goal: 會把邏輯位址拆成頁號和頁內位移、用頁表轉成實體位址；知道分頁沒有外部碎片、但有內部碎片；會用 TLB 命中率算有效存取時間
---
> [!先記住]
> 邏輯記憶體切成一樣大的**頁**，實體記憶體切成一樣大的**頁框**，任何一頁可以放進任何一個頁框。位址切成**頁號＋頁內位移**，用**頁表**把頁號換成頁框號，位移不變。

```fig
bits: 頁號 p 20* | 頁內位移 d 12
cap: 32 位元位址、頁大小 4 KiB（2¹²）：最低 12 位是位移，前 20 位是頁號
```

**分頁**：邏輯位址空間切成一樣大的**頁**，實體記憶體切成一樣大的**頁框**（page frame）。任何一頁可以放進任何一個頁框——**不需要連續**。

位址 $m$ 位元、頁大小 $2^n$：
- 左邊 $m-n$ 位元：**頁號**（page number）→ 查**頁表**得到頁框號
- 右邊 $n$ 位元：**頁內位移**（offset）→ 照抄

?? 填空 | 32 位元的邏輯位址、頁大小 4 KB。頁號有幾位元？
== 20
!! 4 KB＝$2^{12}$，位移 12 位元。
>> $32-12=20$，所以最多 $2^{20}$ 頁。

?? 寫 | 在手寫板：頁大小 1 KB（1024），頁表 [5, 2, 7, 1]（第 0 頁在頁框 5…）。邏輯位址 2100 的實體位址是多少？
== 頁號 $\lfloor2100/1024\rfloor=2$，位移 $2100-2048=52$
== 頁框 7：實體位址 $7\times1024+52=7220$
!! 先除頁大小。
>> 頁號查表、位移照抄。

碎片：
- **沒有外部碎片**（任何空的頁框都能用）
- **有內部碎片**：行程最後一頁通常沒用滿，平均浪費**半頁**

?? 選擇 | 「頁越大，內部碎片越小」對嗎？
[ ] 對
[x] 不對
!! 最後一頁平均浪費多少？
>> 半頁——頁越大浪費越多。頁大的好處是頁表比較小、I/O 比較有效率。

頁表放在記憶體裡，所以**每次存取要讀兩次記憶體**（先讀頁表、再讀資料）。解法：**TLB**——一個很小、很快的快取，存最近用過的「頁號 → 頁框號」。

**有效存取時間**（TLB 查詢 $\varepsilon$、記憶體一次 $m$、命中率 $h$）：
$$\text{EAT}=h(\varepsilon+m)+(1-h)(\varepsilon+2m)$$

?? 填空 | TLB 查詢 20 ns、記憶體 100 ns、TLB 命中率 80%。有效存取時間是多少 ns？
== 140
!! 命中 $20+100$；沒中 $20+200$。
>> $0.8\times120+0.2\times220=96+44=140$。

TLB 沒中只是要**去查頁表**，不代表這頁不在記憶體。

**共享頁**：不會修改自己的程式碼（例如編輯器），多個行程的頁表可以指到同一個頁框，只要放一份。

@例題 同上（TLB 20 ns、記憶體 100 ns），命中率提高到 98%。EAT 是多少？比完全沒有 TLB（每次 200 ns）快多少？
@寫 代公式 | $0.98\times120+0.02\times220=117.6+4.4=122$ ns
@寫 沒有 TLB | 每次 $2\times100=200$ ns
@步 比較 | $200/122\approx1.64$ 倍；只比理想的 100 ns 慢 22%
@答 EAT 122 ns，快約 1.64 倍。

=== os-vm#1
title: 需求分頁：用到才載入
mins: 35
goal: 知道需求分頁的想法和 valid 位元；會寫出處理 page fault 的步驟；會用缺頁率算有效存取時間、知道缺頁率必須極低；知道 dirty 位元的用途
---
> [!先記住]
> 程式不用一次全部放進記憶體，**用到哪一頁才載入哪一頁**。頁表每項多一個 **valid 位元**：0 代表不在記憶體，碰到就發生**缺頁（page fault）**，作業系統把它從磁碟搬進來。

```fig
flow: 存取某頁 -> valid = 0：缺頁 -> 找空頁框
flow: 從磁碟讀進來 -> 改頁表 -> 重新執行那道指令*
```

**需求分頁**（demand paging）：程式開始時不把所有頁都載入，**用到哪一頁才從磁碟讀進來**。這樣程式可以比實體記憶體還大、啟動也快。

頁表每一項有 **valid 位元**：1＝這頁在記憶體裡；0＝不在（或不合法）。存取到 valid＝0 的頁 → **page fault**（缺頁）。

?? 排序 | 處理 page fault 的步驟依序是？
- trap 到 OS，檢查這個存取合不合法（不合法就終止行程）
- 找一個空的頁框（沒有就用頁替換演算法換一個出去）
- 從磁碟把那一頁讀進頁框
- 更新頁表、valid 設成 1
- 重新執行剛才造成 page fault 的那條指令
>> 最後一步很重要：指令要從頭重做。

?? 選擇 | 「TLB 沒中一定會造成 page fault」對嗎？
[ ] 對
[x] 不對
!! TLB 沒中之後去查頁表，這頁可能在記憶體裡嗎？
>> 只有頁表裡 valid＝0 才是 page fault。

**有效存取時間**（缺頁率 $p$、記憶體存取 $ma$）：
$$\text{EAT}=(1-p)\times ma+p\times(\text{處理 page fault 的時間})$$

?? 填空 | $ma=200$ ns、處理 page fault 8 ms（8000000 ns）、缺頁率 $p=0.001$。EAT 大約是多少 ns？（四捨五入到整數）
== 8200
!! $0.999\times200+0.001\times8000000$。
>> $199.8+8000\approx8200$ ns，慢了 40 倍！

?? 寫 | 在手寫板算：同樣的數字，要讓 EAT 不超過 220 ns（慢不到 10%），缺頁率最多是多少？
== $220>(1-p)\cdot200+p\cdot8000000=200+7999800p$
== $p<\frac{20}{7999800}\approx2.5\times10^{-6}$，大約 40 萬次存取才能有一次缺頁
!! 把不等式解出 $p$。
>> 缺頁率必須極低——幸好程式有區域性。

**dirty 位元**（modify bit）：這頁載入後被寫過嗎？要換出去時，沒寫過的直接丟掉（磁碟上的還是對的），省下一次寫回。

@例題 處理一次 page fault：如果被換出的頁是 dirty，要先寫回磁碟（8 ms），再讀入新頁（8 ms）；不是 dirty 只要讀（8 ms）。70% 的時候換出的頁是 dirty。平均處理一次 page fault 要多久？
@寫 兩種情況 | dirty：$8+8=16$ ms；不是 dirty：8 ms
@寫 加權平均 | $0.7\times16+0.3\times8=11.2+2.4=13.6$ ms
@步 意義 | 如果都不是 dirty 只要 8 ms——dirty 位元讓「沒寫過的頁」省了一半時間

=== os-vm#3
title: Thrashing 與工作集
mins: 30
goal: 知道全域和區域替換的差別；能解釋 thrashing 怎麼發生、為什麼加更多行程反而更糟；會算工作集、知道工作集模型和 PFF 怎麼防止 thrashing
---
> [!先記住]
> 頁框太少時，行程一直缺頁、一直等磁碟，CPU 使用率掉下去；作業系統看 CPU 閒就再塞更多行程，情況更糟，這就是 **thrashing**。解法：給每個行程夠用的頁框（**工作集**），不夠就先暫停幾個。

```fig
plane
range: 0 8 0 6 stretch
seg (0.5,0.8) (4,5) hl
seg (4,5) (5,5.2)
seg (5,5.2) (7.5,0.8) bad
text (2,4.2) "越多越忙" hl
text (5.6,3.6) "thrashing" bad
cap: 橫軸：同時跑的行程數（多元程式的程度）；縱軸：CPU 使用率。過了某個點，使用率暴跌
```

有好幾個行程時，頁框怎麼分？
- 平均分、照行程大小**比例**分、照優先權分
- 每個行程有**最少頁框數**（一條指令可能碰到幾頁就至少要幾個）

**全域替換**：可以搶別的行程的頁框（整體效率好，但自己的缺頁率受別人影響）。**區域替換**：只換自己的。

?? 填空 | 62 個頁框，兩個行程大小 10 頁和 127 頁，照比例分配。第一個行程分到幾個頁框？（取整數）
== 4
!! $\frac{10}{137}\times62$。
>> 約 4.5，取 4；第二個約 57。

**Thrashing**：行程的頁框比它**正在用的頁**還少 → 一直缺頁、一直等磁碟：
1. CPU 使用率掉下來
2. OS 以為「CPU 太閒」，加入更多行程
3. 每個行程的頁框更少 → 缺頁更多 → CPU 使用率更低
4. 惡性循環

?? 選擇 | 「增加同時執行的行程數，一定能提高 CPU 使用率」對嗎？
[ ] 對
[x] 不對
!! 行程多到每個都分不到夠用的頁框，會怎樣？
>> 超過某個點就 thrashing，使用率急降。

**工作集**（working set）：最近 $\Delta$ 次存取用到的**不同的頁**。$WSS_i$＝行程 $i$ 的工作集大小；$D=\sum WSS_i$。
- $D>$ 總頁框數 → 暫停（換出）某些行程，避免 thrashing

?? 寫 | 在手寫板：$\Delta=5$，參考串 …2 6 1 5 7 7 7 7 5 1…。在「第一個 7」之後和「最後一個 1」之後，工作集各是什麼？
== 第一個 7 之後：最近 5 次是 2 6 1 5 7 → {1,2,5,6,7}
== 最後一個 1 之後：最近 5 次是 7 7 7 5 1 → {1,5,7}
!! 只看最近 $\Delta$ 次、去掉重複。
>> 工作集大小會隨程式的區域性改變。$\Delta$ 太小抓不到區域性，太大會跨好幾個區域。

**PFF**（page-fault frequency）：直接看缺頁率——高於上限就多給頁框，低於下限就拿走一些。

?? 選擇 | 「工作集模型需要知道未來的存取」對嗎？
[ ] 對
[x] 不對
!! $\Delta$ 是往前看還是往後看？
>> 看的是過去 $\Delta$ 次。

@例題 三個行程的工作集大小是 20、35、40 頁，系統有 80 個頁框。會怎樣？要怎麼處理？
@寫 算 $D$ | $D=20+35+40=95$
@寫 比較 | $95>80$，頁框不夠放全部的工作集 → 有 thrashing 風險
@步 處理 | 暫停一個行程（例如工作集 40 的），剩下 $55\le80$
@答 工作集需求超過頁框，可能 thrashing；依模型暫停一個行程直到 $D\le80$。

=== os-storage#1
title: 磁碟排程：SSTF、SCAN、C-SCAN、LOOK
mins: 35

> [!先記住]
> 磁碟最慢的是**移動磁頭**（搜尋時間）。一堆請求排著時，換個順序服務，磁頭總移動距離可以差很多。**SSTF**（先服務最近的）、**SCAN**（電梯：一路掃到底再回頭）、**C-SCAN**（掃到底後跳回起點，單方向）、**LOOK／C-LOOK**（不用掃到底，到最後一個請求就回頭）。


傳統硬碟讀一筆資料的時間：
$$\text{尋軌時間}+\text{旋轉延遲}+\text{傳輸時間}$$
- **尋軌**：磁頭移到正確的柱面（最慢的部分）
- **旋轉延遲**：等那一格轉到磁頭下面，平均**半圈**

| 演算法 | 做法 |
|---|---|
| FCFS | 照到達順序 |
| SSTF | 先服務**離目前最近**的 |
| SCAN（電梯） | 往一個方向走到底，再折返 |
| C-SCAN | 走到底後**跳回另一端**，永遠同一個方向服務 |
| LOOK／C-LOOK | 只走到最後一個請求就折返（跳回） |

[x] 不對

| 等級 | 做法 | $n$ 顆的可用容量 | 能壞幾顆 |
|---|---|---|---|
| 0 | 只條帶化 | $n$ | 0 |
| 1 | 鏡像 | $n/2$ | 每組 1 顆 |
| 5 | 同位元**分散**在各碟 | $n-1$ | 1 |
| 6 | 兩組同位元 | $n-2$ | 2 |

?? 填空 | 6 顆 2 TB 的硬碟組 RAID 5，可用容量是多少 TB？
== 10
!! $n-1$ 顆。
>> $5\times2=10$ TB。

**還原**：同位元 $P=D_1\oplus D_2\oplus D_3$。$D_2$ 壞了：$D_2=D_1\oplus D_3\oplus P$。

?? 寫 | 在手寫板：$D_1=1011$、$D_2=0110$、$D_3=1100$。算 $P$；再假設 $D_2$ 壞了，用其他三塊算回來。
== $P=1011\oplus0110\oplus1100=0001$
== $D_2=1011\oplus1100\oplus0001=0110$ ✓
!! XOR：一樣是 0，不一樣是 1。
>> 任何一塊都能用其他塊 XOR 回來。

**小寫入**（只改一塊）在 RAID 5 要 **4 次 I/O**：讀舊資料、讀舊同位元、寫新資料、寫新同位元（新 $P$＝舊 $P\oplus$ 舊 $D\oplus$ 新 $D$）。

?? 選擇 | RAID 4 和 RAID 5 的差別是？
[x] RAID 4 的同位元集中在一顆，小寫入時那顆會塞車；RAID 5 分散
[ ] RAID 5 能壞兩顆
[ ] RAID 4 沒有同位元
!! 每次寫都要改同位元。
>> 同位元輪流放，寫入就不會都擠到同一顆。

**RAID 1+0**（先鏡像、再條帶）比 **0+1**（先條帶、再鏡像）可靠：0+1 壞一顆就讓整邊失效。

?? 選擇 | 「RAID 1 的讀取效能比單一硬碟差」對嗎？
[ ] 對
[x] 不對
!! 兩顆有一樣的資料。
>> 可以兩顆同時讀不同的資料，讀取反而快。

@例題 4 顆硬碟的 RAID 5，改一個資料塊。說明需要哪 4 次 I/O，以及新的同位元怎麼算。
@寫 讀 | 讀舊資料 $D_{old}$、讀舊同位元 $P_{old}$
@寫 算 | $P_{new}=P_{old}\oplus D_{old}\oplus D_{new}$（拿掉舊的貢獻、加上新的）
@步 寫 | 寫 $D_{new}$、寫 $P_{new}$
@答 2 讀＋2 寫＝4 次 I/O；$P_{new}=P_{old}\oplus D_{old}\oplus D_{new}$。

=== os-storage#3
title: 檔案配置：連續、鏈結、索引（inode）
mins: 35
goal: 比較連續、鏈結、索引配置的循序存取、隨機存取和缺點；知道 FAT；會算 Unix inode 能支援的最大檔案大小和讀某一塊要幾次 I/O
---
> [!先記住]
> **連續配置**：檔案佔連續的區塊，讀得快但會外部碎裂、不好長大。**鏈結配置**：每塊指向下一塊，不會碎裂但只能循序讀（FAT 把指標集中成一張表）。**索引配置**：用一個索引區塊記所有區塊的位置；Unix 的 **inode** 用直接＋多層間接指標。

```fig
flow: inode -> 12 個直接指標 | 單間接 -> 一塊指標 | 雙間接 -> 指標的指標 | 三間接
cap: 小檔案只用直接指標（快）；大檔案才用到間接指標
```

檔案存在磁碟的哪些區塊？三種方法：

| 方式 | 隨機存取第 $i$ 塊 | 問題 |
|---|---|---|
| **連續** | $O(1)$：起點＋$i$ | 外部碎片；檔案很難長大 |
| **鏈結** | 要從頭走 $i$ 塊 | 每塊要存指標；一個指標壞了後面全丟 |
| **索引** | 讀索引塊後 $O(1)$ | 索引塊要額外空間 |

?? 選擇 | 哪一種配置方式「隨機存取第 1000 塊」最慢？
[ ] 連續
[x] 鏈結
[ ] 索引
!! 要知道第 1000 塊在哪，鏈結要怎麼找？
>> 要從頭跟著指標走 1000 次。

**FAT**：把鏈結的「下一塊是誰」全部集中在一張表裡（放在磁碟開頭，可以快取在記憶體），隨機存取就不用真的讀每一塊。

**Unix inode**（多層索引）：每個檔案一個 inode，裡面有
- 12 個**直接**指標
- 1 個**單層間接**（指向一個存滿指標的區塊）
- 1 個**雙層間接**、1 個**三層間接**

?? 填空 | 區塊 4 KB、指標 4 位元組。一個間接區塊能放幾個指標？
== 1024
!! $4096/4$。
>> 單層間接就能指到 $1024\times4$ KB＝4 MB。

?? 寫 | 在手寫板算：上面的設定下，12 個直接＋單層＋雙層間接，最大檔案多大？
== 直接 $12\times4$ KB＝48 KB；單層 $1024\times4$ KB＝4 MB
== 雙層 $1024^2\times4$ KB＝4 GB；合計約 4 GB＋4 MB＋48 KB
!! 每多一層，乘 1024。
>> 再加三層間接約 4 TB。

小檔案只用直接指標，讀完 inode 就知道資料在哪；大檔案的後段要多讀幾個索引區塊。

?? 選擇 | 用連續配置，檔案要變大但後面的區塊被別人用了。常見的折衷是？
[x] 用 extent：多段連續空間串起來
[ ] 改成鏈結配置
[ ] 不能變大
!! 不用全部連續，一段一段連續就好。
>> 兼顧連續的速度和成長的彈性。

@例題 inode 已經在記憶體。讀檔案第 5000 塊（區塊 4 KB、指標 4 位元組、12 個直接指標），要讀幾次磁碟？
@寫 落在哪一段 | 直接 0～11；單層間接 12～1035；雙層間接從 1036 開始 → 5000 在雙層間接
@寫 讀幾次 | 讀第一層間接區塊、讀第二層間接區塊、讀資料塊
@步 合計 | 3 次
@答 3 次磁碟讀取。

=== os-storage#4
title: 空閒空間管理、目錄與連結
mins: 25
goal: 會算 bitmap 的大小；知道其他空閒空間管理方法；分得清 hard link 和 symbolic link；知道開檔時的兩層表
---
> [!先記住]
> **硬連結**：不同名字指向**同一個 inode**；名字全刪且無開啟參照，檔案才可回收。**軟連結**：一個小檔案，裡面存著另一個檔案的**路徑**，原檔刪了就斷掉。空閒區塊常用**位元圖**記錄。

```fig
array
row 位元圖: 0 0 1 1 1 0 1 1
idx: 0 1 2 3 4 5 6 7
cap: 1 代表空閒（依課本慣例，也有相反的）。區塊 2、3、4 是一段連續的空間
```

**空閒空間**怎麼記？
- **Bitmap**：每個區塊 1 位元（1＝空）。容易找連續空間
- 鏈結串列：空的區塊串起來
- grouping：第一個空區塊存 $n$ 個空區塊的位址
- counting：記（起點, 連續幾塊）

?? 填空 | 1 TB 的磁碟、區塊 4 KB，bitmap 要幾 MB？
== 32
!! 區塊數 $2^{40}/2^{12}=2^{28}$，每塊 1 位元。
>> $2^{28}$ 位元＝$2^{25}$ 位元組＝32 MB。

**連結**：讓同一個檔案出現在兩個地方。
- **Hard link**：另一個目錄項指向**同一個 inode**。硬連結數為 0 且無開啟參照才可回收。不能跨檔案系統；通常不能連到目錄
- **Symbolic link**（軟連結）：一個存「**路徑**」的小檔案。可以跨檔案系統；原檔刪了就變成**懸空連結**

?? 選擇 | 檔案 A 有一個 hard link B。刪掉 A 之後，從 B 還讀得到內容嗎？
[x] 讀得到，inode 的參考計數還有 1
[ ] 讀不到
!! 兩個名字指的是同一個 inode。
>> 如果是 symbolic link，刪掉原檔就讀不到了。

?? 選擇 | 哪一種連結可以跨檔案系統？
[x] Symbolic link
[ ] Hard link
!! inode 編號只在同一個檔案系統裡有意義。
>> 軟連結存的是路徑。

**開檔**時有兩層表：
- **行程層級**的描述元表：每個 fd 指向一個系統開啟描述。
- **系統層級**的開啟描述：記讀寫位置、狀態與 inode。獨立 `open` 建不同描述；`dup` 共用同一描述，所以共用位置。

?? 寫 | 在手寫板：檔案 f 的 inode 參考計數是 1。執行 `ln f g`（hard link）、`ln -s f h`（軟連結）、再 `rm f`。寫出每一步之後 inode 的參考計數，以及 g、h 還能不能讀。
== `ln f g`：計數 2；`ln -s f h`：計數不變（軟連結有自己的 inode）
== `rm f`：計數 1。g 能讀；h 指向路徑 f，已經不存在 → 懸空
!! 軟連結不會增加原檔 inode 的計數。
>> 硬連結數為 0 且無開啟參照，才可回收區塊。

@例題 500 GB 磁碟、區塊 4 KB。用 bitmap 管理空閒空間要多少 MB？如果改成 counting，磁碟上只有 3 段連續空閒空間，要記多少？
@寫 bitmap | 區塊數 $500\times2^{30}/2^{12}\approx1.31\times10^8$ → 約 16 MB
@寫 counting | 3 筆（起點, 長度），每筆幾個位元組
@步 比較 | 空閒空間很集中時 counting 很省；很零碎時 bitmap 比較穩
@答 bitmap 約 16 MB；counting 只要 3 筆。

=== os-storage#5
title: 當機後的一致性：fsck 與日誌
mins: 25
goal: 知道為什麼當機會讓檔案系統不一致；知道 fsck 的缺點；知道日誌式檔案系統怎麼用交易和重放保持一致
---
> [!先記住]
> 改一個檔案要寫好幾個地方（資料、inode、位元圖），寫到一半當機，檔案系統就不一致了。以前開機時用 **fsck** 整個掃一遍修；現在用**日誌（journaling）**：先把要做的修改寫進日誌、標記完成，再真的去改，當機後只要重做日誌裡完成的部分。

```fig
flow: 把修改寫進日誌 -> 寫「交易完成」 -> 真的去改檔案系統 -> 刪掉這筆日誌*
cap: 當機時：日誌裡有「完成」的就重做，沒有的就丟掉
```

建立一個檔案要改好幾個地方：配置 inode、更新目錄、更新空閒空間 bitmap……寫到一半**當機**，這幾個地方就互相矛盾。

**fsck**（一致性檢查）：開機時掃描整個檔案系統，比對目錄、inode、空閒空間。缺點：**很慢**（跟磁碟大小成正比）。

?? 選擇 | fsck 最大的缺點是？
[x] 要掃描整個檔案系統，很慢
[ ] 會刪掉檔案
[ ] 需要額外的硬碟
!! 磁碟越大，掃描越久。
>> 幾 TB 的磁碟可能要掃好幾個小時。

**日誌式檔案系統**（journaling）：
1. 要改 metadata 時，先把「要做的改變」當成一筆**交易**寫進日誌（循序寫，很快）
2. 寫完、標記 **commit**
3. 再真的套用到檔案系統
4. 當機後：只要**重放**已 commit 的交易；沒 commit 的丟掉

?? 排序 | 日誌式檔案系統修改 metadata 的順序
- 把要做的改變寫進日誌
- 在日誌寫下 commit
- 把改變套用到檔案系統的真正位置
- 套用完成後，日誌的這筆可以回收
>> 當機時看日誌：有 commit 就重做，沒有就丟掉。

?? 選擇 | 當機時，一筆交易已經寫進日誌但**還沒 commit**。重開機後怎麼處理？
[x] 丟掉這筆交易
[ ] 重做這筆交易
[ ] 跑 fsck
!! 沒 commit 代表不完整。
>> 檔案系統的真正位置還沒被改，所以丟掉就一致了。

**Log-structured** 檔案系統：更進一步，**所有**寫入都用追加的方式寫在日誌尾端。

?? 寫 | 在手寫板說明：日誌式檔案系統當機後，為什麼只要重放日誌、不用掃描整個磁碟？
== 所有 metadata 的改變都先記在日誌，日誌裡記了「哪些地方可能被改到一半」
== 只要處理日誌裡的交易：有 commit 的重做、沒 commit 的丟掉，其他地方一定是一致的
!! 不一致只可能出現在哪裡？
>> 日誌通常只有幾 MB，幾秒就處理完。

@例題 日誌裡有三筆交易：T1（已 commit、已套用）、T2（已 commit、套用到一半時當機）、T3（還沒 commit）。重開機後怎麼處理？
@寫 T1 | 已經套用完成，可以略過（重放也無妨，操作設計成重做多次結果一樣）
@寫 T2 | 有 commit，**重放**整筆，把沒套用完的補完
@步 T3 | 沒有 commit，丟掉
@答 重放 T2（T1 可略過），丟掉 T3。
